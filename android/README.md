# RepoRead Android app

Kotlin/Compose client: GitHub sign-in through the backend, connected repositories, folder/note browsing, the isolated technical-Markdown reader (outline, footnotes, code tools, note links with previews and backlinks), every note saved for offline use, reading progress with Continue Reading, bookmarks, highlights with notes, recently updated notes, local search, interview-question Practice, spaced Review of cards, and the Notebook. It talks to the backend only through the HTTP/JSON contract in [backend/README.md](../backend/README.md); it never holds GitHub credentials.

This README owns the app's commands and behaviour. Why things are this way is in the [ADRs](../docs/adrs.md), the rules every change keeps in [invariants](../docs/invariants.md), naming and decomposition are in [code style](../docs/code-style.md), and how the app fits with the backend is in the [architecture](../docs/architecture.md).

## Run on the phone

Start PostgreSQL and the backend first (see the backend README). Backend and app contracts must match; deploy the backend before the matching app update. Install reader dependencies once with `npm ci --ignore-scripts` in `android/reader-web`. Then, from the repository root:

```sh
ANDROID_HOME="$HOME/Library/Android/sdk" ./gradlew :app:testDebugUnitTest :app:assembleDebug --no-daemon
~/Library/Android/sdk/platform-tools/adb -s <device-serial> reverse tcp:8081 tcp:8081
~/Library/Android/sdk/platform-tools/adb -s <device-serial> install -r android/build/outputs/apk/debug/app-debug.apk
~/Library/Android/sdk/platform-tools/adb -s <device-serial> shell am start -n com.reporead.android.dev/com.reporead.android.MainActivity
```

Spotless with ktfmt (Kotlin coding conventions, 120 columns; `build.gradle.kts`) owns the app's Kotlin layout. CI runs
`./gradlew :app:spotlessCheck` and `./gradlew :app:lintDebug` before the unit tests; Android Lint treats warnings as
errors, while target SDK and dependency-version notices remain informational because those upgrades are approved
separately. `:app:spotlessApply` rewrites Kotlin files instead. `reader-web`'s JavaScript has no formatter.

Debug builds use the Mac's backend: `adb reverse` makes the phone's `127.0.0.1:8081` reach the Mac's loopback backend, so the registered GitHub callback is unchanged. It is reset when the phone disconnects — including when airplane mode or Wi-Fi loss ends wireless debugging. Re-enable wireless debugging and repeat it before syncing. Only debug builds permit cleartext HTTP, and only to `127.0.0.1` (`src/debug/res/xml/network_security_config.xml` overrides the HTTPS-only `src/main` one). The base URL is a per-build-type `BuildConfig` constant in `build.gradle.kts`.

## Signing and the release APK

Every build — release, debug, and the device-test APK — is signed with one personal key, so each release installs over the last and keeps the phone's data. The debug build is a **separate app**, RepoRead Dev (`com.reporead.android.dev`), installed beside the release app with its own data and sign-in redirect (`reporead-dev://auth`; ADR-12), so testing never touches the app in use. The key is outside the repository; `~/.gradle/gradle.properties` names it (paths only):

```properties
reporead.signing.storeFile=/Users/<you>/.config/reporead/release.jks
reporead.signing.passwordFile=/Users/<you>/.config/reporead/release-keystore-password.txt
```

Both files are mode 0600. It was created with `keytool -genkeypair -keystore … -storetype PKCS12 -alias reporead -keyalg RSA -keysize 4096 -validity 10000 -storepass:file … -keypass:file …` (certificate SHA-256 `20:49:29:9F:…:53:29:3F`). **Back up both files:** without them the next build cannot update the installed app, and installing one signed differently requires uninstalling it, which deletes the phone's saved notes and unsynced changes. Packaging without the properties fails with an explicit message; nothing falls back to the debug key.

```sh
ANDROID_HOME="$HOME/Library/Android/sdk" ./gradlew :app:assembleRelease --no-daemon
~/Library/Android/sdk/platform-tools/adb -s <device-serial> install -r android/build/outputs/apk/release/app-release.apk
```

The release build is not debuggable (no WebView DevTools, no `run-as`) and not minified. It uses the hosted backend, `https://reporead.duckdns.org` (ADR-14), so refreshing and syncing need only an internet connection; saved notes, highlights, and progress work offline and sync later. Its data cannot be inspected on the phone; `run-as` and WebView DevTools work on RepoRead Dev, whose data is its own.

## Releases and Obtainium

A push to `main` that changes the app or the build runs `.github/workflows/android.yml` (also when
`LibrarySnapshotReader.java` or `assetlinks.json` changes, which the build and release check read): formatting and Lint,
unit tests, the reader's check and bundle (`:app:mergeDebugAssets`) and a compile of the device tests, then a release APK signed with the personal key
(`ANDROID_KEYSTORE_BASE64` and `ANDROID_KEYSTORE_PASSWORD`, secrets of the `production` environment, which only `main` may
use), checked against the certificate SHA-256
`2049299f…53293f`, and published as GitHub Release `v0.1.<n>` with `reporead-0.1.<n>.apk` and its `.sha256`. Pull requests
run the same checks, without secrets. `versionCode` is `n`, the commit count of `HEAD` (`git rev-list --count HEAD`), and
`versionName` is `0.1.<n>`, so releases from `main` only go up.

On the phone, [Obtainium](https://github.com/ImranR98/Obtainium) tracks `https://github.com/jaxwong/reporead` (public, so no token) and installs each new release over the current app, keeping its data, because every release is signed with the same key. A release build installed by hand from a branch can carry a higher commit count than the next release from `main`; Android refuses that as a downgrade, so reinstall the release with `adb install -r -d`, and only a release whose database version is at least the hand-installed build's (Room cannot open a newer database).

## HTTP boundary

`network/Api.kt` owns every app-used backend route, its success statuses, response cap and echoed identity checks. Its wire models (`network/wire/`) are generated at build time by the `wireModels` task from `backend/openapi.json`, the backend's published API: response fields are required and nullable ones are still present; optional request fields follow the server's omission declarations. Never edit them; change the backend record and commit the spec its `OpenApiSpecTest` rewrites. `WireRules.kt` owns decoded-answer value rules a generated shape cannot state. `WireJson.kt` owns strict Boolean/Int/Long tokens and ISO instants representable as epoch milliseconds; unknown extra fields remain compatible. `sync/WireMappings.kt` maps typed records to database entities, and `PhoneSync` alone decides which known status/code pairs permanently refuse pending work. `PhoneSync` returns structured refusal facts, disconnect failures and stale-copy fetch failures; Library/Folder/Reader own their UI wording. No raw HTTP verbs or `org.json` network parser remain; the reader bridge keeps its separately owned JSON protocol. See [ADR-26](../docs/adrs.md#adr-26--one-owner-for-the-apps-side-of-the-http-contract).

**Grade-write boundary.** `RepoReadDao` owns admission inside each local grade's write transaction: `saveCardWithFirstReview` checks the current saved bank and existing schedule before writing both rows; `recordReview` checks the current card and answer. The phone does not check a grade's range: the server does (400 `INVALID_REVIEW`, and a `CHECK` on `review_log.grade`), and a grade it refuses stays visible as refused and off the schedule. `PhoneSync.committed` orders operations and protects accepted writes from cancellation; it does not duplicate admission checks.

`ContractTest` covers what generation cannot promise: strict tokens, required-nullable presence and the value rules. Test answers are built with the generated constructors in `src/testShared/` (`WireSamples.kt`, compiled into both the JVM and device tests), so a backend shape change fails their compilation. `RefusalTest` reads the backend's test-only `api-contract/item-refusals.json`. `Api`'s routes are typed by hand: the build puts the spec into the device tests' assets, and `ApiTest` checks every route's method, path, query, statuses and answer type against it, so a changed route fails the device suite. After a backend wire change:

```sh
./gradlew :backend:test --tests '*OpenApiSpecTest' --no-daemon   # rewrites backend/openapi.json once and fails; commit it
ANDROID_HOME="$HOME/Library/Android/sdk" ./gradlew :app:testDebugUnitTest --no-daemon
```

`logging/DeviceLog.kt` owns logcat and the bounded durable device-log store. Its `pending.jsonl` and `sending.jsonl`
filenames and each line's `{at, appVersion, level, message}` JSON remain readable across app updates;
`sync/DeviceLogUploadWorker.kt` makes at most two `POST /api/app-logs` calls per run: the batch a failed run left, then the lines stored since. A failed call is not retried; the next request (start, leaving the screen, a warning while no batch is claimed, or a crash) sends its lines. It finishes a claim only after 204 or
the route's permanent
`INVALID_REQUEST` refusal; an unanswered call leaves that claim replayable, and signed-out work leaves it untouched.

## Device tests

These run against in-memory databases on the phone: the Room cache and pending-change rules, the Room migrations from exported schemas, the sync, the background sync's outcomes, and grade push against a test-only HTTP server on a loopback port, isolated WebView reader and study checks, Activity-recreation tests of the reader, Practice sessions and Review, and the app's back stack through the real `RepoReadApp` (`AppNavigationTest`). The screen tests run in `TestHostActivity`, a debug-only, non-exported Activity absent from release builds, and use explicitly test-only saved pages; they never access the app's database, and the network they reach is a test-only server on loopback. Compose assertions use `createEmptyComposeRule()` beside `ActivityScenario`: the host needs its content set before it launches, which `createAndroidComposeRule` does not allow. Install and run them with adb, which keeps the installed app and its data:

```sh
ANDROID_HOME="$HOME/Library/Android/sdk" ./gradlew :app:assembleDebug :app:assembleDebugAndroidTest --no-daemon
~/Library/Android/sdk/platform-tools/adb -s <device-serial> install -r android/build/outputs/apk/debug/app-debug.apk
~/Library/Android/sdk/platform-tools/adb -s <device-serial> install -r -t android/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
~/Library/Android/sdk/platform-tools/adb -s <device-serial> shell am instrument -w com.reporead.android.dev.test/androidx.test.runner.AndroidJUnitRunner
```

They need the debug build (RepoRead Dev) installed; the release app is untouched. Keep the phone unlocked and the test Activity visible until the UI suite finishes; the lock screen, another app or the notification shade can intercept its actions and cause timeouts. `./gradlew :app:connectedDebugAndroidTest` runs the same tests but **uninstalls RepoRead Dev afterwards**, deleting its session, cache, and any unsynced changes. `am instrument` exits 0 even when tests fail: the run passed only if it ends with `OK (n tests)`.

Navigation restoration tests pass a real Activity saved-instance-state Bundle through a Parcel into a fresh debug host,
using the same format policy as `MainActivity`. The historical string-list fixture is constructed from the old saver
format, not captured from an old APK. `EntryLifetimeTest` probes real Navigation 3 decorators with labelled test-only
ViewModels; the production screens' work now belongs to their entry owners (ADR-28). PR4's saved-state format 2 reset
format 1's incompatible Compose-owned session/UI state. Audit PR1 advances it to 3 because format 2 may contain the
retired figure destination. The study-package moves advance it to 4 because saved sessions name the former
`library.StudySession` class. This database type/package move advances it to 5 because reader overlays may serialize
the former entity class names. Navigation, drafts and in-progress sessions reset once; Room, files and pending
mutations are untouched.
[ADR-27](../docs/adrs.md#adr-27--navigation-3-owns-the-back-stack-saved-screen-state-belongs-to-its-entry-and-its-format)
and ADR-28 record decisions and executed evidence.

### Historical live verification

The scratch-note live-write harness was removed after review: its recovery path could send unrelated pending work
from the real store. It is not replaced by a hidden script or a second harness. This deliberately removes automated
live-write replay; the maintained device suites use isolated stores and loopback HTTP. Earlier approved live results
remain historical evidence in [API contract PR #70](https://github.com/jaxwong/reporead/pull/70),
not instructions to run the deleted tests. Future live writes require separately scoped approval.

### Real-corpus check

`InterviewBankCorpus` checks question recognition against every page of a real notes repository, rendered by the backend's `RenderedCorpus` harness (see [backend/README.md](../backend/README.md#verify)). It fails by name on a bank question without an answer line, an answer line without a link, or a link to a note with no page. Run it after adding interview folders; its output stays outside the repository:

```sh
REPOREAD_STUDY_PAGES=<dir>/pages ANDROID_HOME="$HOME/Library/Android/sdk" ./gradlew :app:testDebugUnitTest --tests '*InterviewBankCorpus' --rerun --no-daemon -i
```

## Behavior

- **Sign-in:** a Chrome Custom Tab opens `/app/sign-in` with a PKCE challenge; the code the server redirects with is exchanged with the verifier for a bearer session. The release app receives it at `https://reporead.duckdns.org/app/signed-in`, a verified App Link that Android opens only in the app signed with the key the server's `.well-known/assetlinks.json` names (`adb shell pm get-app-links com.reporead.android` shows the verification); RepoRead Dev receives it at `reporead-dev://auth`, since the Mac's loopback backend has no domain to verify. The session is encrypted with an Android Keystore AES-GCM key; one that can never be read again is deleted (sign in again; saved notes stay), and any other Keystore failure fails that request and keeps it (ADR-22). A 401 (expired session, or a GitHub sign-in the server can no longer renew) signs the app out of the network only: saved notes stay readable and the library offers **Sign in with GitHub**. **Sign out…** attempts to revoke the server session (and, on the last signed-in device, RepoRead's GitHub authorization), then clears only the stored session. A 401 means the session already ended; other revocation failures are logged, not retried, and the server session expires within 30 days. Account deletion reports success and explicitly clears the session only on confirmation; an unconfirmed deletion reports its failure, and a 401 can independently end the session. Every outcome keeps this phone's saved notes, images, highlights, cards, grades, bookmarks, positions and unsent changes. `Account` owns sign-in, sign-out and deletion in the application scope, at most one server call per operation; it neither owns nor removes local data (ADR-22). Sign-in validates and consumes the pending PKCE verifier before exchange, records no data owner and leaves saved data alone. A different account replaces acknowledged lists at its first sync, but old unsent changes can be sent under that account: the accepted one-account limit ([known gaps](../docs/feature-list.md#known-gaps)). Account messages remain until dismissed, independently of refresh and rotation; account operations keep navigation and entry state. Sign-out and delete-account confirmations are both saveable UI state. `RepoReadApplication` owns one `PhoneSync` per process, shared by activity and workers, and launches its startup image sweep on first creation. Saved images are kept only for known snapshots Room holds a page of; sweeps also run after library replacement, a fetched open, a successful Save all loop under cancellable `locked` and a disconnect. Save all does not sweep the full image tree after each page or on failure/cancellation; the next library refresh, Library open or startup sweeps orphans.
- **Add repository:** lists the repositories GitHub lets both you and the RepoRead App read; **Connect** adds one. A connected one shows **Update**, which connects it again under GitHub's current name and default branch and keeps its notes, progress and highlights: the way back after renaming either on GitHub, whose redirects for the old name RepoRead does not follow.
- **Offline cache (Room):** repositories, document lists, and the latest complete rendered copy of each opened note, one per document (the blob SHA records its Markdown version; `snapshotCommitSha` pins images and embed resolution). **Save all notes on this phone** (a repository's overflow menu) fetches, one note at a time, every note whose saved copy is missing, has another blob or path, uses an older page format, or depends on another repository snapshot (repository images or blocked embeds), using the saved note list (refresh the repository first to pick up GitHub changes). The server limits a complete saved page (HTML, canonical search blocks and metadata) to 1 MiB of UTF-8. It runs as WorkManager work once the phone has a network, whether or not any screen is open; each folder screen of the repository shows that it is waiting, how far it has got, or how its last run ended. A note the server refuses to render (too large) is counted and skipped without replacing an older saved copy. A run Android stops part-way (after about 10 minutes, or when the network goes) starts again and fetches only what is still missing; an unreachable server, a 5xx or GitHub unavailable is tried again as the background sync is, and any other failure ends the run, keeping the copies already saved, so running again continues. While it waits or runs, its repository menu offers **Stop saving notes**, which awaits cancellation and keeps the saved pages; refresh and disconnect are available afterwards. A long failure explanation is shortened with an ellipsis before it is stored in WorkManager, so the failure still reports its progress within the 10 KiB output limit. Account operations do not cancel or prune Save all; signed-out requests end the run like any other non-retryable failure, keeping completed pages. It also checks images on every listed saved page, including already-current pages, one page and one image at a time through `SavedPageImages` (at most 64 distinct image requests per page, the server's reference limit). Cached images need no request. Permanent content/image refusals skip the rest of that page's image pass and count the page once as skipped, keeping its text. Other image API failures end the run and use the same worker retry/stop boundary as content failures: unreachable/5xx retry within its existing limit; 401 stops with a sign-in reason and no further image requests. No fallback request is made. Progress counts every listed page checked; a page counts as saved only with every image on disk. A saved image file is not read, only found. A page or image the phone's storage cannot write (a full disk) stops the run at once with "RepoRead couldn't write to this phone's storage; it may be full.", keeping what was saved; it is not retried. The online reader still shows an image it could not write. A note whose cached blob, path and page format are current opens without a network call; a known matching repository snapshot is also required when its HTML contains `/repo-image/` or `image-blocked`. Unrelated commits do not invalidate text-only pages, and a legacy text-only page does not need snapshot metadata. Otherwise the current version is fetched; if that fails, the older saved copy is shown with the reason. Failed refreshes never replace saved lists or notes. There is no eviction yet; every saved note's latest version is kept (on the Pixel, 653 notes take 28.8 MB).
- **Reading position:** the reader saves the first block visible at the top of the screen (heading path, 64-character text prefix, block index) and scroll percent 0.7 s after scrolling stops, when the app goes to the background, and when leaving the note. Once captured, the bounded local database write runs on the app's own scope (`RepoReadApplication.scope`), so it finishes after leaving the note or rotating the phone; it does not start a network sync. It records the blob SHA actually displayed; refreshing a repository never changes it. Restoring tries heading + text, text, section, block index, then percent, and says when it is approximate or when the note changed since the last read. The system font size is applied to the reader.
- **Annotation capacity:** the server admits 500 combined highlights/cards per document and 5,000 per user, excluding bookmarks. A 422 `ANNOTATION_LIMIT` keeps the capped creation at the head of the queue with its mutation id and first grades retained. Later creations and their grades wait; each sync spends one GitHub blob call on that same creation until existing annotations are deleted to free capacity. Grades for acknowledged cards and reading/bookmark sends can still proceed. No client-side count duplicates the server's rule.
- **Continue reading and bookmarks:** the library shows the five most recently read notes and all bookmarks. Saves and bookmark toggles are stored locally as pending and sent by the background sync; a bookmark tap on a note disconnected while open reports that it was not saved; pending changes win over older server state and yield to newer state.
- **Pending-change delivery:** every local change (reading position, bookmark, highlight or card, offline delete, grade) asks WorkManager for one pending-change send once the phone has a network, 5 s after the last change, also when the app is closed; it sends what waits as opening the library does, but loads no lists, which the screens do. An unreachable server, a 5xx, or GitHub unavailable is tried again with exponential backoff from 30 s, at most 10 attempts; any other failure (signed out, access denied) waits for the next change or library open, which show it. Android may defer the run (Doze, app standby, Battery Saver), and a force-stop pauses it until the app is opened; on the Pixel, adaptive Battery Saver holds it until the app is opened or the phone charges unless RepoRead's battery usage is set to Unrestricted. While changes wait, the library says how many, with **Send changes**; pull to refresh also sends changes then reloads the library. Activity and workers enter the application's one `PhoneSync` directly. Its existing lock orders local changes and server answers independently of account operations.
- **What one sync does when something fails:** pending highlight and card creations are sent first; they need GitHub, so when sending them fails for any reason but an unreachable server (typically GitHub or access to it failing: 503, 403, a GitHub sign-in the server can no longer renew) they wait and the rest of the sync — grades, reading positions, bookmarks, then the server's library — still runs. When the server refuses one item (400, 404, 409, 410, or 422 with a RepoRead error code, except 409 `REPOSITORY_RENAMED`, which waits for the repository to be connected again) that item is marked and the sync goes on: a refused highlight or grade shows its reason; a refused bookmark change is undone; the library's status line names them. Well-formed reading positions are accepted with timestamps clamped to [1970, server now]; a confirmed 404 drops a position, while malformed input stops the pass and stays pending. Any other failure ends the sync with everything unacknowledged still pending: an unreachable server (only a request that got no answer counts as unreachable), or a response that breaks the app's contract (a missing field, a null or a number where text is required, a malformed time). The library is one request (`GET /api/library`), whose lists the server reads from one database snapshot; the phone writes all of it in one transaction, or none of it when the request fails or its answer breaks the contract. Its complete lists replace the phone's: every repository's notes, removed ones included (marked removed, they name the reading positions, bookmarks and highlights kept on them, and no list of notes shows them); a repository it no longer lists (for example, disconnected on another device, or a disconnect whose answer was lost) is forgotten with its notes; and acknowledged reading positions it no longer has are removed. Finally, saved copies of notes that no repository lists now and that no reading position, bookmark, or highlight refers to are deleted with their images, so such a copy no longer turns up in search.
- **Highlights and notes:** select text within one block and choose **Highlight** or **Add note** from the selection menu. A selection that cannot be used (across two blocks) stays on screen with its handles and the reason, so it can be adjusted. The selection is read through `evaluateJavascript` using ADR-05's contract (block id, UTF-16 offsets into canonical text); the page still cannot call native code, and a page script that throws is raised with its own error rather than read as nothing. A new highlight is saved locally as a pending creation with a client mutation id in one Room write, then sent immediately and again by the background sync, each library open, or note open until the server acknowledges it — the same id every time, so a lost acknowledgement cannot duplicate it. A refusal (e.g. the text no longer matches) is kept and shown, not retried. **Notes** lists the note's highlights with Show, Edit note, and Delete (which asks first; a card's review history goes with it), then **Linked from**: the notes whose saved copies link to this one, found on the phone (offline) by resolving every saved page's note links as a tap would; a link that could mean several notes counts. It says when only some of the repository's notes are saved, since the others' links are unknown. Editing and deleting acknowledged highlights are online only; a conflicting edit shows both texts and asks which to keep. The reader's dialogs and sheets (a question or note being written, an edit, a deletion, a conflicting edit, a link's preview or choices, the outline) are one state, so at most one is open, and it is kept across rotation with what was typed; a highlight being reattached is kept too (ADR-25). Study, Show and a changed section's link are offered only once the page is ready, and not at all on a page that did not finish rendering. Deleting a highlight or card the server has not acknowledged yet works offline: it disappears at once and is marked for deletion, and the next sync replays its creation (the server may already have it after a lost acknowledgement) and deletes it there, so a late answer or the server's list cannot bring it back; one changed elsewhere first is shown again instead. Each highlight is drawn at the server's current location for it when that location is in the displayed version; a pending creation is drawn where it was made. A highlight the server re-anchored after an edit says what its text is now. An **orphaned** highlight (the note changed and the passage could not be found reliably) shows its original selection with its context and a **Reattach** button: select the passage in the note, then choose **Reattach here** from the selection menu (online; the server verifies the selection). Notes removed from the repository are labelled in Continue reading and Bookmarks; their history and highlights are kept.
- **Search:** searches only what is on the phone: every listed note's title and path, the text of saved notes, and highlights with their notes. With nothing typed it says how many notes are searched by their text, for example "Searching 653 of 654 notes by their text".
- **Links between notes:** tapping an Obsidian `[[link]]` or a relative `.md` link resolves it like Obsidian against the repository's saved note list (works offline): an exact path, a name with a folder, or a file name, preferring the linking note's folder. One match opens a **preview** sheet: title, folder, and the saved copy from its start or from the linked heading, in a separate isolated page where nothing navigates; **Open** opens the note. Without a saved copy the sheet says so (Open fetches it). When several notes share the name the app asks which one and opens it. A `#Heading` opens the note at that heading instead of the saved position (a heading that is gone opens it at the saved position and says so); it may be the heading's text (Obsidian) or its GitHub anchor (`#2-separate-the-contracts-and-checks`, repeats numbered `-1`, `-2`). An unknown name says so. A same-note Markdown link (`[text](#heading)`), in the note or a footnote's sheet, scrolls to that heading in the page, or says it is missing. `![[image.png]]` embeds bind once by name in the saved page's captured repository snapshot. Refresh the repository and page to pick up image changes; missing or ambiguous names remain visibly unavailable, never guessed during fetching.
- **Outline and current section:** the top bar's subtitle is the heading of the section at the top of the screen, updated 150 ms after scrolling settles. **Outline** lists the note's headings by level with the current one marked; tapping one scrolls to it. Headings are read from the page through `evaluateJavascript`, like the reading position.
- **Study view (P3):** **Study** appears only on LeetCode notes with a recognized heading. `Problem` stays visible; `Approach`, `Brute Force Approach`, `Optimized Approach`, `Complexities`, and `Mistakes` collapse until tapped. **Read** leaves study view. Blocks keep their canonical text; a collapsed section's heading stands in for hidden content when saving/restoring, and jumping to a highlight reveals its section. Study mode survives activity recreation but is not a stored preference. Interview banks open as ordinary notes; they are practised in Practice.
- **Practice (Library):** questions come only from **interview banks**: notes in a folder named `interview` (at any depth). A topic is the folder holding an interview folder (e.g. `core/databases` for `core/databases/interview/`); **All topics** mixes them. In a bank, an H3 is a question when its section (up to the next H1–H3) has exactly one `Canonical answer:` line, and its text is the heading without a leading `N. `; with a `Canonical path:` line, the heading and its top-level list items, numbered in bank order, are one question over that line; with no items it asks the heading alone. Section names and numbers only label (the section shows as the level, e.g. Foundations). An H3 with no such line or several (questions written as H4s), a Canonical line under no H3, and later prompts repeating a Canonical line are not questions and are named under their topic. Their count expands into warnings grouped by bank. Tapping a warning opens its exact block, including a stray answer line, using the document id and saved Markdown version rather than a path or heading-text lookup. If that version or block is no longer displayed, the reader keeps its saved position and explains why; it never jumps to a same-named heading or a reused block id. Each topic shows its new and scheduled questions and how many of its listed banks are up to date; it never fetches notes. A bank saved at an older version than the listed one counts as not saved: its questions wait until it is saved again, since their grades would be refused. A session asks the topic's **new** questions (those without a card on the review schedule; a card the server refused is on none, so its question is asked again), shuffled one per bank per round, one at a time: the question alone; **Show answer** shows the bank's other lines (what the interviewer is testing, what a complete answer covers) and the core section each link on the answer line points to, alone, from the copy saved on this phone (one tab per link; **Open note** opens it at that heading); then Again (0), Hard (3), Good (4), Easy (5) under it, each showing the days until the question is due again. The first grade saves the question as a card whose answer is its whole Canonical line in the asked version, plus that grade in one Room transaction; both are local and pending until sent. Matching uses this bank document and the card's drawn text, not the prompt. A re-anchored Canonical-line edit can keep its card; a larger edit can leave an orphan on the schedule beside a new question. Two prompts over one line keep the first in bank order and warn on the later prompt, while identical prompts over different lines stay distinct. A concurrent or restored submission for a line already on this phone's schedule writes nothing. Practice and Review confirm only the Canonical line; linked sections are supplementary and labelled as saved copies. A question graded Again comes back at the end of the session until answered right (Hard, Good or Easy), without saving again. The session survives recreation; Practice and Review share how a session moves (`study/StudySession.kt`, ADR-20). Recognition belongs to `study/InterviewBank.kt` (jsoup over saved HTML); the session makes **0 external calls**.
- **Review (P4, in Practice):** cards come only from a Practice question's first grade (the reader's **Make a question** was deleted on 2026-10-21); creation uses the existing pending annotation mutation and idempotent push. The Practice tab's first row is **Review**: how many cards are due (and how many need their bank saved first), then how many fall due tomorrow, or on the next day with cards, and how many in the 7 days after today, recomputed at local midnight and whenever the app returns to the screen (also catching a time-zone change); the Practice tab icon shows the due count. It opens **Review**: the same line, **All topics** with every due card, and each topic with cards due and how many. A topic opens a session of its due cards (All topics, of every topic's), shuffled and interleaved by note, capped at the phone's `SESSION_LIMIT` of 40; it does not wait for a Library answer and works offline from the saved cards and review log. A card asks the question its Canonical line has in the bank's current saved version, with that version's answer; when the bank no longer has the line, it shows its saved question and offers the bank instead. Each card shows its question alone, then **Show answer** (Practice's answer view), then the grades under it, each showing the days until the card is due again (none on a card asked again, whose grade is not saved). A card's first grade in the session is saved as one local pending UUID, written completely even if recreation cancels the UI; one graded Again comes back later in the session, unsaved, until answered right. The log, not the queue, says which cards have a saved grade, so recreation never saves one twice. A due card that cannot be graded is shown with one fix per reason (`CardBlock`, the first reason that applies being the one to fix first): open the note to save its current version, or open the bank that no longer asks its line. A card the server refuses, or whose note is removed, during a session says so and points to deleting it in its note's Highlights and notes; such cards start no session (Notebook lists them). Grades are sent by the background sync and when Library opens, after card creations; timestamps are clamped to [1970, server now], and acknowledgements replace the local timestamp. A refused grade is visible and excluded from scheduling, not retried.
- **Changed cards:** a card is an interview-bank question (the reader no longer makes cards), so a new version of its bank is never confirmed. Review reads the card's question, answer and version from the bank's current saved copy by its Canonical line; a card whose line is no longer there shows its saved prompt and offers the bank with **Open note**, where the server re-anchors an edited line or the card can be deleted. A bank whose current version is not saved blocks its cards until it is saved. Offline, only the last known repository version is available; unseen GitHub edits cannot be detected until refresh. The sole pure scheduler is `study/ReviewSchedule.kt`, a fixed ladder of gaps: 1, 3, 7, 14, 30, 60, 120 days. Again returns a card to the first step, Hard steps back one (not below the first), Good climbs one and Easy two, capped at 120 days; a new card starts on the first step, so its first grade gives Hard 1, Good 3 and Easy 7 days. A card is due from the start of the phone's local day its gap ends on, so a card graded in the evening is due the next morning. In a session, a card's first grade is saved; one graded Again comes back later in the same session, unsaved, until answered right; a saved Again puts it back on the first step, due the next day. A grade the server refused is not counted and can be dismissed in Review. Review opens on the cards due by topic; a session covers one topic or all of them.
- **Notebook:** Library's **Notebook** shows every cached highlight/card, including removed notes and pending creations, with folder (including descendants), note and orphan filters. Library sync fetches the complete server notebook without GitHub calls. **Open passage** opens the reader at the saved annotation and shows Notes; missing/orphaned passages remain available there for reattachment. Nothing is written to GitHub.
- **Tables and diagrams:** wide content scrolls sideways in the page.
- **Footnotes:** a footnote reference shows its number (in definition order); tapping it shows the definition in a sheet at the bottom of the page without scrolling; tapping elsewhere closes it. Definitions stay where the note has them, each on its own line. The sheet is outside the note's blocks, so it cannot be highlighted or saved as the reading position.
- **Bars hide while reading:** a swipe that scrolls the note down at least 24 dp hides the top bar and the system bars when the finger lifts; one that scrolls up 24 dp, or ends near the top (also by a fling), shows them; a swipe from the screen edge shows the system bars briefly. They change only when the finger lifts: moving the WebView under a finger still on it made the page read the move as scrolling the other way, and the bars and page oscillated. Only scrolling that follows a touch on the page counts, so restoring the position, jumping from the outline, or **Show** never hides them. Driven by the WebView's own scroll and touch callbacks (the WebView does not take part in Compose nested scrolling). Leaving the reader shows the system bars.
- **Code blocks:** a row above each code block shows its language, **Copy**, and — while the code is wider than the screen — **Wrap** (layout only; not remembered). Copy is a same-origin `/copy-code?block=…` link the app intercepts; it reads the block's canonical text through `evaluateJavascript` and copies it without the final line break, so a pasted command does not run. The row is outside the block, so canonical text is unchanged.
- **Images:** repository images referenced by a note are fetched through the backend by native code (the page never sees the token) and cached by document, immutable repository commit and resolved path, never by the Markdown blob alone. The reader and answer preview use the displayed page's snapshot. Migrated legacy pages with unknown identity keep their text but show no images until refreshed; old blob-keyed image files are deleted, never read as a fallback. A failed cache read shows unavailable without trying the network; cache reads and deletion share the existing lock. Offline and uncached, an image shows `[Image unavailable: …]`; remote images are blocked.
- **Reader isolation:** backend-sanitized HTML in a WebView with app-bundled reader/Mermaid/highlight assets only, no credentials, no JavaScript bridge, and no network/file/content access. Tapped `http(s)` links open the browser; links between notes are not followed.
