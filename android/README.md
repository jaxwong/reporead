# RepoRead Android app

Kotlin/Compose client: GitHub sign-in through the backend, connected repositories, folder/note browsing, the isolated technical-Markdown reader (outline, footnotes, code tools, full-screen figures, note links with previews and backlinks), every note saved for offline use, reading progress with Continue Reading, bookmarks, highlights with notes, what changed since the version last read, local search, interview-question Practice, spaced Review of cards, and the Notebook. It talks to the backend only through the HTTP/JSON contract in [backend/README.md](../backend/README.md); it never holds GitHub credentials.

This README owns the app's commands and behaviour. Why things are this way is in the [ADRs](../docs/adrs.md), the rules every change keeps in [invariants](../docs/invariants.md), and how the app fits with the backend in the [architecture](../docs/architecture.md).

## Run on the phone

Start PostgreSQL and the backend first (see the backend README). Install reader dependencies once with `npm ci --ignore-scripts` in `android/reader-web`. Then, from the repository root:

```sh
ANDROID_HOME="$HOME/Library/Android/sdk" ./gradlew :app:testDebugUnitTest :app:assembleDebug --no-daemon
~/Library/Android/sdk/platform-tools/adb -s <device-serial> reverse tcp:8081 tcp:8081
~/Library/Android/sdk/platform-tools/adb -s <device-serial> install -r android/build/outputs/apk/debug/app-debug.apk
~/Library/Android/sdk/platform-tools/adb -s <device-serial> shell am start -n com.reporead.android.dev/com.reporead.android.MainActivity
```

Spotless with ktfmt (Kotlin coding conventions, 120 columns; `build.gradle.kts`) owns the app's Kotlin layout. CI runs `./gradlew :app:spotlessCheck` before the unit tests; `:app:spotlessApply` rewrites the files instead. `reader-web`'s JavaScript has no formatter.

Debug builds use the Mac's backend: `adb reverse` makes the phone's `127.0.0.1:8081` reach the Mac's loopback backend, so the registered GitHub callback is unchanged. It is reset when the phone disconnects — including when airplane mode or Wi-Fi loss ends wireless debugging. Re-enable wireless debugging and repeat it before syncing. Only debug builds permit cleartext HTTP, and only to `127.0.0.1` (`src/debug/res/xml/network_security_config.xml` overrides the HTTPS-only `src/main` one). The base URL is a per-build-type `BuildConfig` constant in `build.gradle.kts`.

## Signing and the release APK

Every build — release, debug, and the device-test APK — is signed with one personal key, so each release installs over the last and keeps the phone's data. The debug build is a **separate app**, RepoRead Dev (`com.reporead.android.dev`), installed beside the release app with its own data and sign-in redirect (`reporead-dev://auth`; ADR-12), so testing never touches the app in use. The key is outside the repository; `~/.gradle/gradle.properties` names it (paths only):

```properties
reporead.signing.storeFile=/Users/<you>/.config/reporead/release.jks
reporead.signing.passwordFile=/Users/<you>/.config/reporead/release-keystore-password.txt
```

Both files are mode 0600. It was created with `keytool -genkeypair -keystore … -storetype PKCS12 -alias reporead -keyalg RSA -keysize 4096 -validity 10000 -storepass:file … -keypass:file …` (certificate SHA-256 `20:49:29:9F:…:53:29:3F`). **Back up both files:** without them the next build cannot update the installed app, and installing one signed differently requires uninstalling it, which deletes the phone's saved notes and unsynced changes. Packaging without the properties fails with an explicit message; nothing falls back to the debug key.

```sh
ANDROID_HOME="$HOME/Library/Android/sdk" ./gradlew :app:assembleRelease --no-daemon
~/Library/Android/sdk/platform-tools/adb -s <device-serial> install -r android/build/outputs/apk/release/app-release.apk
```

The release build is not debuggable (no WebView DevTools, no `run-as`) and not minified. It uses the hosted backend, `https://reporead.duckdns.org` (ADR-14), so refreshing and syncing need only an internet connection; saved notes, highlights, and progress work offline and sync later. Its data cannot be inspected on the phone; `run-as` and WebView DevTools work on RepoRead Dev, whose data is its own.

## Releases and Obtainium

A push to `main` that changes the app or the build runs `.github/workflows/android.yml` (also when `Library.java` or `assetlinks.json` changes, which the build and release check read): unit tests, the reader's check and bundle (`:app:mergeDebugAssets`) and a compile of the device tests, then a release APK signed with the personal key (repository secrets `ANDROID_KEYSTORE_BASE64` and `ANDROID_KEYSTORE_PASSWORD`), checked against the certificate SHA-256 `2049299f…53293f`, and published as GitHub Release `v0.1.<n>` with `reporead-0.1.<n>.apk` and its `.sha256`. Pull requests run the same three checks, without secrets. `versionCode` is `n`, the commit count of `HEAD` (`git rev-list --count HEAD`), and `versionName` is `0.1.<n>`, so releases from `main` only go up.

On the phone, [Obtainium](https://github.com/ImranR98/Obtainium) tracks `https://github.com/jaxwong/reporead` (public, so no token) and installs each new release over the current app, keeping its data, because every release is signed with the same key. A release build installed by hand from a branch can carry a higher commit count than the next release from `main`; Android refuses that as a downgrade, so reinstall the release with `adb install -r -d`, and only a release whose database version is at least the hand-installed build's (Room cannot open a newer database).

## Device tests

These run against in-memory databases on the phone: the Room cache and pending-change rules, the Room migrations from exported schemas, the sync, the background sync's outcomes, and grade push against a test-only HTTP server on a loopback port, isolated WebView reader and study checks, and Activity-recreation tests of the reader, Practice sessions and Review. The lifecycle tests use a debug-only, non-exported Activity and explicitly test-only saved pages; they never access the app's database, and only the sync tests reach the network, on loopback. The host is absent from release builds. Install and run them with adb, which keeps the installed app and its data:

```sh
ANDROID_HOME="$HOME/Library/Android/sdk" ./gradlew :app:assembleDebug :app:assembleDebugAndroidTest --no-daemon
~/Library/Android/sdk/platform-tools/adb -s <device-serial> install -r android/build/outputs/apk/debug/app-debug.apk
~/Library/Android/sdk/platform-tools/adb -s <device-serial> install -r -t android/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
~/Library/Android/sdk/platform-tools/adb -s <device-serial> shell am instrument -w com.reporead.android.dev.test/androidx.test.runner.AndroidJUnitRunner
```

They need the debug build (RepoRead Dev) installed; the release app is untouched. `./gradlew :app:connectedDebugAndroidTest` runs the same tests but **uninstalls RepoRead Dev afterwards**, deleting its session, cache, and any unsynced changes. `am instrument` exits 0 even when tests fail: the run passed only if it ends with `OK (n tests)`.

### Real-corpus check

`StudyCorpus` checks question recognition against every page of a real notes repository, rendered by the backend's `RenderedCorpus` harness (see [backend/README.md](../backend/README.md#verify)). It fails by name on a bank question without an answer line, an answer line without a link, or a link to a note with no page. Run it after adding interview folders; its output stays outside the repository:

```sh
REPOREAD_STUDY_PAGES=<dir>/pages ANDROID_HOME="$HOME/Library/Android/sdk" ./gradlew :app:testDebugUnitTest --tests '*StudyCorpus' --rerun --no-daemon -i
```

## Behavior

- **Sign-in:** a Chrome Custom Tab opens `/app/sign-in` with a PKCE challenge; the code the server redirects with is exchanged with the verifier for a bearer session. The release app receives it at `https://reporead.duckdns.org/app/signed-in`, a verified App Link that Android opens only in the app signed with the key the server's `.well-known/assetlinks.json` names (`adb shell pm get-app-links com.reporead.android` shows the verification); RepoRead Dev receives it at `reporead-dev://auth`, since the Mac's loopback backend has no domain to verify. The session is encrypted with an Android Keystore AES-GCM key; one that can never be read again is deleted (sign in again; saved notes stay), and any other Keystore failure fails that request and keeps it (ADR-22). A 401 (expired session, or a GitHub sign-in the server can no longer renew) signs the app out of the network only: saved notes stay readable and the library offers **Sign in with GitHub**. **Sign out and remove from phone…** first says how many changes on the phone never reached the server; confirming revokes the session (and, on the last signed-in device, RepoRead's GitHub authorization) and deletes this phone's cached notes, images, and those unsynced changes. Confirming records a pending removal on disk first; then the session is revoked, removed from the phone, and the phone's copy deleted. From the tap until Room's rows and every file are gone only the account screen shows, the phone signs in as no account, the screen says where the removal stands with **Retry**, and the next start finishes it. Account deletion records the removal only once the server confirms; a refused, unanswered or interrupted deletion, or a 401, keeps everything on the phone. A sign-in over data with no recorded owner validates and consumes its pending verifier before removing the data; an unsolicited callback leaves it untouched. `Account` owns these operations and the current local-copy lifetime (ADR-22). A decided local removal retires the old Sync/image instance permanently; new screens receive a fresh one only after successful cleanup. Local changes, server answers and export publication share its existing lock. Old screen work is cancelled rather than admitted after re-sign-in. Account messages remain until explicitly dismissed, independently of refresh status and rotation. Saved images are kept only for the known repository snapshots Room holds a page of; a sweep deletes the rest after a sync, after a page is saved, after a disconnect, at a clear and at each start.
- **Add repository:** lists the repositories GitHub lets both you and the RepoRead App read; **Connect** adds one. A connected one shows **Update**, which connects it again under GitHub's current name and default branch and keeps its notes, progress and highlights: the way back after renaming either on GitHub, whose redirects for the old name RepoRead does not follow.
- **Offline cache (Room):** repositories, document lists, and the latest complete rendered copy of each opened note, one per document (the blob SHA records its Markdown version; `snapshotCommitSha` pins images and embed resolution). **Save all notes on this phone** (a repository's overflow menu) fetches, one note at a time, every note whose saved copy is missing, of another version or repository snapshot, or of an older page format, using the saved note list (refresh the repository first to pick up GitHub changes). The server limits a complete saved page (HTML, search text and metadata) to 1 MiB of UTF-8. A note the server refuses to render (too large) is listed and skipped without replacing an older saved copy; any other failure, or leaving the screen, stops the run and keeps the copies already saved, so running again continues. Images are not fetched by it; they are saved when the note is read online, and one that cannot be saved (a full disk) is still shown. A note whose cached version, path, repository snapshot and page format are current opens without a network call. Any known repository commit change invalidates freshness, even with unchanged Markdown; this conservative rule avoids another image-change index. Otherwise the current version is fetched; if that fails, the older saved copy is shown with the reason. Failed refreshes never replace saved lists or notes. There is no eviction yet; every saved note's latest version is kept (on the Pixel, 653 notes take 28.8 MB).
- **Reading position:** the reader saves the first block visible at the top of the screen (heading path, 64-character text prefix, block index) and scroll percent 0.7 s after scrolling stops, when the app goes to the background, and when leaving the note. Once captured, the bounded local database write runs on the app's own scope (`RepoReadApplication.scope`), so it finishes after leaving the note or rotating the phone; it does not start a network sync. It records the blob SHA actually displayed; refreshing a repository never changes it. Restoring tries heading + text, text, section, block index, then percent, and says when it is approximate or when the note changed since the last read. The system font size is applied to the reader.
- **Continue reading and bookmarks:** the library shows the five most recently read notes and all bookmarks. Saves and bookmark toggles are stored locally as pending and sent by the background sync; pending changes win over older server state and yield to newer state.
- **Background sync:** every local change (reading position, bookmark, highlight or card, offline delete, grade) asks WorkManager for one sync once the phone has a network, 5 s after the last change, also when the app is closed; it sends what waits as opening the library does, but loads no lists, which the screens do. An unreachable server, a 5xx, or GitHub unavailable is tried again with exponential backoff from 30 s, at most 10 attempts; any other failure (signed out, access denied) waits for the next change or library open, which show it. Android may defer the run (Doze, app standby, Battery Saver), and a force-stop pauses it until the app is opened; on the Pixel, adaptive Battery Saver holds it until the app is opened or the phone charges unless RepoRead's battery usage is set to Unrestricted. While changes wait, the library says how many, with **Sync now**; pull to refresh does the same. Activity and worker share Account's startup: an interrupted removal is finished before any pending upload. A busy/stopped removal starts no ordinary background work. One operation at a time uses the local copy's lock; retirement rejects queued/later work and clearing waits for admitted work before a fresh copy is published.
- **What one sync does when something fails:** pending highlight and card creations are sent first; they need GitHub, so when sending them fails for any reason but an unreachable server (typically GitHub or access to it failing: 503, 403, a GitHub sign-in the server can no longer renew) they wait and the rest of the sync — grades, reading positions, bookmarks, then the server's library — still runs. When the server refuses one item (400, 404, 409, 410, or 422 with a RepoRead error code, except 409 `REPOSITORY_RENAMED`, which waits for the repository to be connected again) that item is marked and the sync goes on: a refused highlight or grade shows its reason; a refused reading position stays on this phone, pending, and is offered again; a refused bookmark change is undone; the library's status line names them. Any other failure ends the sync with everything unacknowledged still pending: an unreachable server (only a request that got no answer counts as unreachable), or a response that breaks the app's contract (a missing field, a null or a number where text is required, a malformed time). The library is one request (`GET /api/library`), whose lists the server reads from one database snapshot; the phone writes all of it in one transaction, or none of it when the request fails or its answer breaks the contract. Its complete lists replace the phone's: every repository's notes, removed ones included (marked removed, they name the reading positions, bookmarks and highlights kept on them, and no list of notes shows them); a repository it no longer lists (for example, disconnected on another device, or a disconnect whose answer was lost) is forgotten with its notes; and acknowledged reading positions it no longer has are removed. Finally, saved copies of notes that no repository lists now and that no reading position, bookmark, or highlight refers to are deleted with their images, so such a copy no longer turns up in search.
- **Highlights and notes:** select text within one block and choose **Highlight** or **Add note** from the selection menu. A selection that cannot be used (across two blocks) stays on screen with its handles and the reason, so it can be adjusted. The selection is read through `evaluateJavascript` using ADR-05's contract (block id, UTF-16 offsets into canonical text); the page still cannot call native code, and a page script that throws is raised with its own error rather than read as nothing. A new highlight is saved locally as a pending creation with a client mutation id in one Room write, then sent immediately and again by the background sync, each library open, or note open until the server acknowledges it — the same id every time, so a lost acknowledgement cannot duplicate it. A refusal (e.g. the text no longer matches) is kept and shown, not retried. **Notes** lists the note's highlights with Show, Edit note, and Delete (which asks first; a card's review history goes with it), then **Linked from**: the notes whose saved copies link to this one, found on the phone (offline) by resolving every saved page's note links as a tap would; a link that could mean several notes counts. It says when only some of the repository's notes are saved, since the others' links are unknown. Editing and deleting acknowledged highlights are online only; a conflicting edit shows both texts and asks which to keep. The reader's dialogs and sheets (a question or note being written, an edit, a deletion, a conflicting edit, a link's preview or choices, the outline) are one state, so at most one is open, and it is kept across rotation with what was typed; a highlight being reattached is kept too (ADR-25). Study, Show and a changed section's link are offered only once the page is ready, and not at all on a page that did not finish rendering. Deleting a highlight or card the server has not acknowledged yet works offline: it disappears at once and is marked for deletion, and the next sync replays its creation (the server may already have it after a lost acknowledgement) and deletes it there, so a late answer or the server's list cannot bring it back; one changed elsewhere first is shown again instead. Each highlight is drawn at the server's current location for it when that location is in the displayed version; a pending creation is drawn where it was made. A highlight the server re-anchored after an edit says what its text is now. An **orphaned** highlight (the note changed and the passage could not be found reliably) shows its original selection with its context and a **Reattach** button: select the passage in the note, then choose **Reattach here** from the selection menu (online; the server verifies the selection). Notes removed from the repository are labelled in Continue reading and Bookmarks; their history and highlights are kept.
- **Changes since last read:** the library marks Continue reading entries "Updated since you read", lists every read note whose current version (in the saved note lists) is not the one last read, and lists the five most recently changed other notes as "Not read yet" or "Read", each with when a refresh saw it change. Opening a note whose last-read version differs from the displayed one shows **Changed since you last read**: changed, new, and removed sections with line counts; tapping a current section scrolls to its heading. The summary starts from the oldest version read whose changes have not been shown yet: moving to a newer version keeps the one left behind as a phone-only baseline until a summary from it has loaded on screen, so opening the note offline, signed out, or leaving before the summary loads does not use it up, and the note stays in Updated since you read. Online only and not cached; a failure is shown with **Try again**. A note never read shows nothing.
- **Search:** searches only what is on the phone: every listed note's title and path, the text of saved notes, and highlights with their notes. With nothing typed it says how many notes are searched by their text, for example "Searching 653 of 654 notes by their text".
- **Links between notes:** tapping an Obsidian `[[link]]` or a relative `.md` link resolves it like Obsidian against the repository's saved note list (works offline): an exact path, a name with a folder, or a file name, preferring the linking note's folder. One match opens a **preview** sheet: title, folder, and the saved copy from its start or from the linked heading, in a separate isolated page where nothing navigates; **Open** opens the note. Without a saved copy the sheet says so (Open fetches it). When several notes share the name the app asks which one and opens it. A `#Heading` opens the note at that heading instead of the saved position (a heading that is gone opens it at the saved position and says so); it may be the heading's text (Obsidian) or its GitHub anchor (`#2-separate-the-contracts-and-checks`, repeats numbered `-1`, `-2`). An unknown name says so. A same-note Markdown link (`[text](#heading)`), in the note, a footnote's sheet or a full-screen figure, scrolls to that heading in the page, or says it is missing. `![[image.png]]` embeds bind once by name in the saved page's captured repository snapshot. Refresh the repository and page to pick up image changes; missing or ambiguous names remain visibly unavailable, never guessed during fetching.
- **Outline and current section:** the top bar's subtitle is the heading of the section at the top of the screen, updated 150 ms after scrolling settles. **Outline** lists the note's headings by level with the current one marked; tapping one scrolls to it. Headings are read from the page through `evaluateJavascript`, like the reading position.
- **Study view (P3):** **Study** appears only on LeetCode notes with a recognized heading. `Problem` stays visible; `Approach`, `Brute Force Approach`, `Optimized Approach`, `Complexities`, and `Mistakes` collapse until tapped. **Read** leaves study view. Blocks keep their canonical text; a collapsed section's heading stands in for hidden content when saving/restoring, and jumping to a highlight reveals its section. Study mode survives activity recreation but is not a stored preference. Interview banks open as ordinary notes; they are practised in Practice.
- **Practice (Library):** questions come only from **interview banks**: notes in a folder named `interview` (at any depth). A topic is the folder holding an interview folder (e.g. `core/databases` for `core/databases/interview/`); **All topics** mixes them. In a bank, an H3 is a question when its section (up to the next H1–H3) has exactly one `Canonical answer:` (or `Canonical answers:`) line, and its text is the heading without a leading `N. `; with a `Canonical path:` line, each top-level list item under it is a question, with the heading as its instruction. Section names and numbers only label (the section shows as the level, e.g. Foundations). An H3 with no such line or several (questions written as H4s), a path with no items, and a Canonical line under no H3 are not questions and are named under their topic. Their count expands into warnings grouped by bank. Tapping a warning opens its exact block, including a stray answer line, using the document id and saved Markdown version rather than a path or heading-text lookup. If that version or block is no longer displayed, the reader keeps its saved position and explains why; it never jumps to a same-named heading or a reused block id. Each topic shows its new and scheduled questions and how many of its listed banks are up to date; it never fetches notes. A bank saved at an older version than the listed one counts as not saved: its questions wait until it is saved again, since their grades would be refused. A session asks the topic's **new** questions (those without a card on the review schedule; a card the server refused is on none, so its question is asked again), shuffled one per bank per round, one at a time: the question alone; **Show answer** shows the bank's other lines (what the interviewer is testing, what a complete answer covers) and the core section each link on the answer line points to, alone, from the copy saved on this phone (one tab per link; **Open note** opens it at that heading, and a table's or diagram's **Full screen** opens it as in the reader); then Again (0), Hard (3), Good (4), Easy (5) under it, each showing the days until the question is due again. The first grade saves the question as a card whose answer is its whole Canonical line in the asked version, plus that grade, both local and pending until sent; a question already having a card (same bank, prompt and answer line) is never saved twice, so identical prompts with different answers stay distinct. A question graded Again comes back at the end of the session until answered right (Hard, Good or Easy), without saving again. The session survives recreation; Practice and Review share how a session moves (`library/StudySession.kt`, ADR-20). Recognition belongs to `reader/Study.kt` (jsoup over saved HTML); the session makes **0 external calls**.
- **Review (P4, in Practice):** cards come from a Practice question's first grade, from selecting an answer in a note and choosing **Make a question**, or from **Make a question** on a highlight in Notes (write a question; the selected canonical passage is its answer). Question/answer authoring survives recreation; creation uses the existing pending annotation mutation and idempotent push. The Practice tab's first row is **Review**: how many cards are due (and how many need checking first), then how many fall due tomorrow, or on the next day with cards, and how many in the 7 days after today, recomputed at local midnight and whenever the app returns to the screen (also catching a time-zone change); the Practice tab icon shows the due count. It opens a session of the due cards, shuffled and interleaved by note, capped by the server's notebook response (40); before any Library sync has delivered that, it says to open Library online. Each card shows its question alone, then **Show answer** (the passage in its block's context, or for a bank question Practice's answer view), then the grades under it, each showing the days until the card is due again (none on a card asked again, whose grade is not saved). A card's first grade in the session is saved as one local pending UUID, written completely even if recreation cancels the UI; one graded Again comes back later in the session, unsaved, until answered right. The log, not the queue, says which cards have a saved grade, so recreation never saves one twice. A due card that cannot be graded is shown with one fix per reason (`CardBlock`, the first reason that applies being the one to fix first): open the note to save its current version, to reattach an orphan, or so that the server places the card in the new version; sync a card not sent yet; or confirm its answer there with **Answer is still right** (confirmed by the server, so online only). A card the server refuses, or whose note is removed, during a session says so and points to deleting it in its note's Highlights and notes; such cards start no session (Notebook lists them). Grades are sent by the background sync and when Library opens, after card creations; a refused grade is visible and excluded from scheduling, not retried.
- **Changed cards:** every known note-version change blocks review until the answer is resolved, saved locally, and explicitly confirmed (online): **Answer is still right**, in Notes or when Review shows the card's fix. The server places a card in a new version only when the note's highlights are listed (ADR-06), which opening the note does and a sync does not, so Review sends such a card to its note with **Open note**. This conservative rule also covers edits elsewhere in the answer's section without relying on an unavailable diff. Orphans use the existing selection-based **Reattach** path, then need confirmation. Conflicting server metadata and a stale local note list also block review. Offline, only the last known repository version is available; unseen GitHub edits cannot be detected until refresh. The sole pure scheduler is `library/ReviewSchedule.kt`, a fixed ladder of gaps: 1, 3, 7, 14, 30, 60, 120 days. Again returns a card to the first step, Hard keeps its step, Good climbs one and Easy two, capped at 120 days; a new card starts one below the first, so Good gives 1 day and Easy 3. A card is due from the start of the phone's local day its gap ends on, so a card graded in the evening is due the next morning. In a session, a card's first grade is saved; one graded Again comes back later in the same session, unsaved, until answered right; a saved Again puts it back on the first step, due the next day. A grade the server refused is not counted and can be dismissed in Review.
- **Notebook:** Library's **Notebook** shows every cached highlight/card, including removed notes and pending creations, with folder (including descendants), note and orphan filters. Library sync fetches the complete server notebook without GitHub calls. **Open passage** opens the reader at the saved annotation and shows Notes; missing/orphaned passages remain available there for reattachment. **Export Markdown** shares the filtered entries as a UTF-8 `.md` attachment via a non-exported FileProvider limited to `files/exports/`. Quotes preserve their exact characters, blank lines, CRLF, Unicode and trailing whitespace. Export writes an immutable file atomically before sharing; failures are shown. Private export files are deleted at each app start and on sign-out, disconnect or account deletion; an app that reads a shared export only after that finds it gone, and copies already shared to other apps are outside RepoRead's control. Nothing is written to GitHub.
- **Footnotes:** a footnote reference shows its number (in definition order); tapping it shows the definition in a sheet at the bottom of the page without scrolling; tapping elsewhere closes it. Definitions stay where the note has them, each on its own line. The sheet is outside the note's blocks, so it cannot be highlighted or saved as the reading position.
- **Bars hide while reading:** a swipe that scrolls the note down at least 24 dp hides the top bar and the system bars when the finger lifts; one that scrolls up 24 dp, or ends near the top (also by a fling), shows them; a swipe from the screen edge shows the system bars briefly. They change only when the finger lifts: moving the WebView under a finger still on it made the page read the move as scrolling the other way, and the bars and page oscillated. Only scrolling that follows a touch on the page counts, so restoring the position, jumping from the outline, or **Show** never hides them. Driven by the WebView's own scroll and touch callbacks (the WebView does not take part in Compose nested scrolling). Leaving the reader shows the system bars.
- **Code blocks:** a row above each code block shows its language, **Copy**, and — while the code is wider than the screen — **Wrap** (layout only; not remembered). Copy is a same-origin `/copy-code?block=…` link the app intercepts; it reads the block's canonical text through `evaluateJavascript` and copies it without the final line break, so a pasted command does not run. The row is outside the block, so canonical text is unchanged.
- **Full-screen tables and diagrams:** a table wider than the screen and every rendered diagram has **Full screen** above it (a same-origin `/full-screen?figure=…` link the app intercepts). The figure opens alone with pinch zoom, system bars hidden, and rotation following the phone even when auto-rotate is off; leaving it restores the app's orientation. It is a separate isolated page built from the saved copy of the version the reader showed (same resources, no bridge, no navigation), so it survives the recreation that rotating causes. Highlights are not drawn or made there.
- **Images:** repository images referenced by a note are fetched through the backend by native code (the page never sees the token) and cached by document, immutable repository commit and resolved path, never by the Markdown blob alone. The reader, answer preview and full-screen figure all use the displayed page's snapshot. Migrated legacy pages with unknown identity keep their text but show no images until refreshed; old blob-keyed image files are deleted, never read as a fallback. A failed cache read shows unavailable without trying the network; cache reads and deletion share the existing lock. Offline and uncached, an image shows `[Image unavailable: …]`; remote images are blocked.
- **Reader isolation:** backend-sanitized HTML in a WebView with app-bundled reader/Mermaid/highlight assets only, no credentials, no JavaScript bridge, and no network/file/content access. Tapped `http(s)` links open the browser; links between notes are not followed.

`reader-web/` holds the reader's display JavaScript and styles; see its README. `schemas/` holds exported Room schemas; version 2 adds `annotations` through a Room auto-migration, verified on the Pixel against an existing version 1 database; version 3 adds highlight locations, status, and original context, and the `deleted` flag on reading states and bookmarks (auto-migration with defaults); version 4 adds a note's refresh-found change time (`changedAt`, nullable), verified on the Pixel against its existing version 3 database; version 5 adds saved notes' search text; version 6 adds their page format (`renderFormat`), so a saved copy from an older format is fetched once more when opened online; version 7 adds card metadata, pending/durable review log projections and the server-owned session limit (auto-migration); version 8 adds phone-only change baselines and the `deleting` mark for unacknowledged creations (auto-migration, regression-tested from the exported v7 schema). Version 9 drops saved notes' `commitSha`, which nothing read (auto-migration with `@DeleteColumn`). Version 10 keeps each saved page's note links in `note_links`, filled from the pages already saved as it migrates, so Linked from never reads pages. Version 11 replaces a highlight's `pending`, `rejection`-as-state and `deleting` flags with one `state` (a hand-written migration, `ANNOTATION_STATE_10_11`, since each row's state is computed from its flags; `LocalStore.open` applies it). Version 12 drops a bookmark's `sourceBlobSha`, the version bookmarked, which nothing read (auto-migration with `@DeleteColumn`). Version 13 keeps a note's title, path, current version and removal only in its `documents` row, which gains `deleted` and now keeps removed notes too; reading states, bookmarks and highlights drop their copies (auto-migration with `@DeleteColumn`), and saved notes start as listed until the next sync says otherwise. Version 14 adds nullable `notes.snapshotCommitSha` (auto-migration): existing text, note links, annotations and pending changes survive, while a legacy page's image snapshot remains explicitly unknown. A v13-to-v14 device regression verifies this policy. The instrumented regression constructs the exported v6 schema in a test-only database, migrates it to the current version, and verifies saved notes and unsent highlights survive.
