# RepoRead — Architecture decision records

The decisions that shape RepoRead, as built. Each says what was decided, why, and what it costs, with its evidence summarised in place. Status of all: **accepted**. A later decision amends an earlier one in place and says when.

`docs/` is the single source of truth for decisions ([this file](adrs.md)), scope and status ([feature list](feature-list.md)), user needs ([user stories](user-stories.md)), the rules every change keeps ([invariants](invariants.md)) and how the parts fit ([architecture](architecture.md)). The [backend](../backend/README.md) and [Android](../android/README.md) READMEs own contracts, commands and behaviour detail. The implementation spec, build plan, post-MVP plan and per-stage verification records these ADRs used to cite were removed on 2026-10-14; what they decided is recorded here, and their full command logs remain in Git history (for example `git show 2e434f7:requirements/reporead-stage4-record.md`).

## ADR-01 — A Spring Boot backend between the phone and GitHub

**Context.** The phone could call GitHub directly. But annotations, reading state, document identity across edits, and re-anchoring need durable server-side state and decisions, and a GitHub credential on the phone would sit next to untrusted rendered Markdown.

**Decision.** One Spring Boot/PostgreSQL service (a modular monolith: `auth`, `github`, `repository`, `sync`, `document`, `reading`, `annotation`, `deletion`, `library`, `observability`) owns users, connections, logical documents, reading state, annotations, and every reconciliation decision. The Android app (Kotlin/Compose, Room) talks to it only through explicit HTTP/JSON contracts; no JVM classes are shared, and each side defines its own request and response shapes.

- **Languages.** Kotlin because the client is a native Android app, which gives direct control over text selection, scrolling, lifecycle, offline storage and secure storage. Java for the backend because a learning goal is to understand Spring Boot deeply without Kotlin-specific Spring behaviour at the same time. Android first; iOS is out of scope.
- **Monolith.** One developer, one operational unit, strong transactions over application state, easy local debugging, and no demonstrated need for independent deployment. Packages are by capability, not technical layer. Separation would need evidence, not aesthetics.
- **Request validation** (2026-10-15). Each route checks its own input by hand and refuses it with its own code (`INVALID_VERSIONS`, `INVALID_ANNOTATION`, ...). Bean Validation (`spring-boot-starter-validation`) was not adopted: most checks relate fields to each other or to the server's clock, which annotations express poorly, and moving the single-field ones would split validation into two styles and replace their codes with a generic `INVALID_REQUEST`.
- **Error text** (2026-10-17). A failure is a stable code plus a message that says what happened and names no client's screens or controls. The app's `describe()` (`Api.kt`) is the one place that words a code for its screens, falling back to the server's message. Before, some server messages told the user to "tap Update under Add repository" while the app worded other codes itself and the reader special-cased `ANNOTATION_CONFLICT`. A case whose fix the app must name gets its own code: GitHub's redirect of a call that names a repository (branch, tree, blob, image), which follows a rename of the repository or branch, is 409 `REPOSITORY_RENAMED`, which the app words as **Update**. A redirect of a listing names no repository and stays `GITHUB_INVALID_RESPONSE`. The code, not the status, decides what happens to waiting work: a rename never heals by retrying, so background sync stops the run (it retries only unreachable and 5xx), and `refusesItem()` excludes the code, so a waiting highlight or card is kept for after the reconnect instead of being marked refused. (A first version sent it as 502 so that work stayed pending, which also made background sync retry calls that could not succeed.)
- **Persistence.** Spring JDBC with hand-written SQL; Flyway owns the schema (`backend/src/main/resources/db/migration`). The original spec's Spring Data JPA was not adopted; no reason was recorded at the time, and this rationale was written on 2026-10-14 from the code as built. The queries that carry correctness are PostgreSQL-specific: `ON CONFLICT` upserts for idempotent sync and mutations, `FOR UPDATE` row locks, `RETURNING`, and `jsonb` columns. Under JPA these would be native queries or custom type mappings anyway. Rows are flat and read by id or user, so entity mapping, relationships and dirty checking would save little, and they would bring flush timing, lazy loading and a second schema description (entities alongside Flyway). Transaction boundaries are explicit `TransactionTemplate` blocks in the class that owns the table being written, which takes that write's row locks inside them; controllers open none, and each lock method refuses to run outside a transaction, where its lock would be released as soon as it is taken (amended 2026-10-16: before, the block was "at the call site", which was a controller for some writes and the owner for others, and nothing checked that a lock ran inside one). `@Transactional` is not used: one mechanism, and `RepositorySnapshotRefresh` must call GitHub before its transaction in the same method, which a block says directly.
- **Ownership** (2026-10-17). Each table has one owner class, which makes every write to it and takes the locks those writes need; any class may read another owner's tables in a join or a count (a read-only projection), so SQL reads cross owners while Java imports have no cycles. Controllers check their input and shape the response; owners make every GitHub call and decide the rules: a repository's image is fetched by `Attachments`, and which repositories a user may connect is decided by `RepositoryConnections`, through the user's own token.

**Consequences.** The phone needs the backend for refreshes and sync; saved content stays readable without it. Release builds reach the hosted service (ADR-14); debug builds reach the developer's Mac through `adb reverse` (ADR-12). Contract compatibility is an explicit concern because nothing is shared.

## ADR-02 — GitHub is canonical and read-only; note bodies are not stored on the server

**Decision.** RepoRead never writes to GitHub repositories: the App has read-only permissions (ADR-16), and the backend's GitHub client issues only GET requests, apart from OAuth token exchange and renewal and revoking RepoRead's own authorization for a user who signs out of their last device or deletes their account (ADR-03). The server stores document metadata (paths, titles, blob SHAs) and the user's own state, and fetches a note's exact blob by SHA whenever it renders or compares it; nothing is cached server-side, and there is no table of document versions. Every GitHub operation has a stated call ceiling; a failed call ends the operation without an alternative strategy, retry or backoff.

**Consequences.** Opening a note online costs one GitHub request. A version GitHub no longer has (rewritten history) is reported as unavailable, never reconstructed. Highlights necessarily store their quoted text (ADR-11).

## ADR-03 — GitHub user tokens stay on the server, encrypted at rest

**Context.** The GitHub App's user token is the only credential that reads private notes. Giving it to the phone exposes it beside untrusted content. Kept only in memory (the original decision), it was lost on every restart, and once the backend was hosted every deploy restarted it, so each push to `main` meant signing in again.

**Decision.** The backend keeps the token and GitHub's refresh token in PostgreSQL (`github_tokens`, one row per GitHub user), each encrypted with AES-256-GCM under a key file outside the database (`REPOREAD_GITHUB_TOKEN_KEY_FILE`, 0600, like the client secret) and bound to its user, and gives the phone an opaque bearer session (hash stored, Keystore-encrypted on the phone). GitHub App user tokens last 8 hours, so the backend renews one that expires within a minute before using it, as mobile apps with short-lived access tokens do. No installation-token fallback. Amended 2026-10-13 twice: renewal (before, every expiry meant a new sign-in, about once a day), then storage at rest (before, every restart did).

**Consequences.** Restarts and deploys keep the sign-in. GitHub refusing a renewal (the refresh token expired after about 6 months or was revoked) requires signing in again (401 `SIGN_IN_REQUIRED`); database-only operations keep working. Any other failed renewal, unanswered or a refusal of the server's own credentials (a wrong client secret), fails that request (503 `GITHUB_UNAVAILABLE`) and keeps the stored token, which works again once GitHub answers or the secret is fixed; signing out and deleting the account never wait on it (amended 2026-10-17: a refused secret was a 500 that also broke both). A database copy without the key file holds no usable credential; losing or replacing the key file makes every stored token unreadable, and each user signs in again. Signing out of the last device, or deleting the account, revokes RepoRead's authorization on GitHub (all of its tokens for that user) and removes the stored token, leaving RepoRead holding no credential; if GitHub does not confirm the revocation, the stored token is removed anyway and GitHub expires the tokens itself. The next sign-in shows GitHub's authorization screen again.

**Evidence.** Real browser sign-in and user-scoped repository eligibility on 2026-10-02 (Stage 0); `GitHubTokenRefreshTest`, `GitHubTokensTest`.

**Lifecycle amendment (2026-10-18).** Refresh-only per-user locking left OAuth token exchange/storage and last-device
revocation/account deletion unordered. Revoking a grant invalidates *all* that user's app tokens, so guarding storage
alone cannot fix the race. `GitHubTokenLifecycle` now owns one process-wide gate from callback entry through token
persistence, and through renewal, app-code exchange, session removal and committed account deletion/revocation. A
callback's identity is not known before exchange; one gate is simpler than identity discovery plus a lock registry
for this single-process, allowlisted service. It is entered before SQL transactions, not around entire repository
operations. Queued session changes revalidate admission; last-device removal also invalidates earlier pending app
codes atomically. Encrypted storage and external-call ceilings are unchanged. See the backend README for the exact
runtime contract and the [API contract PR #70](https://github.com/jaxwong/reporead/pull/70) for race/failure evidence.

## ADR-04 — The server renders; an isolated WebView displays

**Decision.** Java (CommonMark with the GFM tables, strikethrough and task-list extensions; escaped raw HTML; a jsoup tag/attribute/URL safelist) is the single owner of parsing, sanitizing, canonical block text, and limits. The phone shows that HTML in a WebView, with Compose for everything around it:

- a local HTTPS asset origin (`appassets.androidplatform.net`), a CSP, and app-bundled scripts and styles only (highlight.js, Mermaid); no CDN requests. The CSP's `style-src` allows `'unsafe-inline'` because Mermaid builds its SVG with style attributes and a `<style>` element; Markdown can add neither (raw HTML is escaped and the safelist allows no `style`), and `script-src` stays `'self'`;
- blocked navigation, network, file and content access; no JavaScript bridge; no credentials;
- repository images fetched by native code, which attaches the bearer token itself;
- a renderer that crashes or that Android reclaims ends only its page: the reader says the page stopped, and preview and answer pages show their failure text;
- Mermaid in strict security mode with HTML labels disabled, within the server's diagram bounds. A diagram that fails shows its error and source; no alternate renderer is tried. The rendered SVG is display only: the diagram's source is the anchorable block. Mermaid, with the KaTeX it brings, is 3.4 of the 3.6 MB of script, so it is a second script that only a page with a diagram loads (2026-10-17): a page without one opens in about 0.1 s instead of 0.2–0.7 s, and a page with one about 0.1–0.2 s later than before.

**Initial visibility** (amended 2026-10-20, performance PR2, Step 3). The reader stays transparent until its study layout, highlights and saved position or one-time target are applied and the native visual-state barrier completes. JavaScript returning from a scroll does not mean the next native frame has caught up. A missing target retains the existing saved-position restoration and notice. Failed/timed-out pages become visible with controls and position saving disabled; renderer loss retains its existing removal/message path. A page that cannot draw may remain hidden: there is no timed reveal of stale content. Release and renderer loss end the opening work. `ReaderPage` owns the shared native barrier and viewport clipping; the reader and each preview/answer host own their visibility. Each isolated native page owns cancellable rendering work that ends before destruction or on renderer loss; the reader uses its existing opening job. Late browser results cannot resume released page work. The reader saves its opened position only after the barrier; if it stops in that window, nothing new is saved and the last saved position stands. Positioning rules, readiness-poll limits, save ownership and navigation state are unchanged.

**Why.** Chosen at Stage 0 (closed 2026-10-06) after a reader spike on the Pixel 8a: a real private note rendered by Java (200 blocks, 4 diagrams) showed 0 diagram errors and matching canonical text in the WebView, and a finger selection returned exactly the expected UTF-16 range. The spike modules were then deleted.

**Limit ownership (2026-10-20).** GitHubHttpConfiguration bounds incoming blobs. MarkdownRenderer owns structural limits, not a duplicate blob-size or HTML-byte check. After one serialization, `DocumentController.Content` admits the complete saved page (HTML, canonical search blocks and metadata) at the existing 1 MiB UTF-8 ceiling. Removing `PageOutput` means expanded HTML is allocated before rejection; this is a transport/storage ceiling, not a peak-heap guarantee. Canonical facts are still extracted without serializing a page.

**Consequences.** One parser defines what a selection means for both reader and server. Unsupported or oversized content is a visible error, not executed. Remote images are blocked. The page reaches native code only through intercepted same-origin links (ADR-18).

## ADR-05 — Anchors are block ids and UTF-16 offsets into canonical text of one version

**Decision.** A selection is `{sourceBlobSha, blockId, startOffset, endOffset, exactText}` within one block, offsets in UTF-16 units of the Java-exported canonical text. The server verifies it against that exact version and derives context and heading path itself. Block ids are stable only within a version.

**The text contract.**

- **Canonical text** is not raw Markdown: inline formatting contributes its visible text, a soft line break becomes a space, a hard break one LF, code keeps its whitespace, and nothing is Unicode-normalized. The exported blob SHA must match the exact UTF-8 source bytes.
- **Anchorable blocks** are paragraphs, headings, code fences, table cells, and list items without nested candidate blocks. Blocks do not overlap. Ids `b0`, `b1`, … are deterministic within one source version only.
- **Offsets** are zero-based, start-inclusive and end-exclusive; a surrogate pair is two units, and no range the server stores, or context it cuts, ends between them: a selection that would is refused.
- **The page** compares its text with the exported canonical text; a mismatch is an invariant failure, never an approximate anchor. The page leaves a selection's leading and trailing whitespace out of its anchor, and an empty or whitespace-only selection produces none (amended 2026-10-22, ADR-17).

**Consequences.** Cross-block selections are refused. Every later version needs re-anchoring (ADR-06). Any rendering change must leave an unchanged blob's canonical text identical (ADR-18). Known gaps: a tight list item with nested points has its own text in no block, so it cannot be highlighted; the server checks that `sourceBlobSha` is a blob in the document's repository that renders the selection, not that it belongs to that document's history.

## ADR-06 — Re-anchor only on measured evidence; otherwise orphan

**Context.** US-07: a wrong attachment is worse than a lost one, but orphaning every light edit fails the story.

**Decision.** Resolve in order — whole block unchanged (SHA-256 of a block text unique in its version), unchanged position with unchanged context, exact quote singled out by context, bounded fuzzy match — with thresholds chosen by measurement, not by hand. Anything weaker is `ORPHANED`, keeping the original selection and context for manual reattachment. The original anchor never changes.

**Measurement (2026-10-06).** `Anchoring.MEASURED` = quote context 0.5, unique-quote length 16, fuzzy quote 0.85, fuzzy context 0.8, chosen with `AnchorMeasurement` over a read-only clone of the real notes repository (640 notes, 599 real edited versions). Four samples of about 22,000 labelled cases each (one for tuning, three held out): **0 wrong attachments**, 95.0–95.6% of should-attach cases attached. Unchanged blocks 100%; inserted, moved or duplicated blocks 97–98%; an edit far from the selection 100%, next to it 91%; a one-character edit 94%; a one-word edit 56%; deletions and rewrites orphaned. All 133 attachments in real history were checked by hand: none wrong. Recall on real changed blocks is not measured. Rerun 2026-10-15 on the grown repository (799 notes, 891 real edited versions, 28,796 labelled cases), before and after locations were required to carry their evidence (identical output): 0 wrong attachments, 21,377 of 22,373 should-attach cases attached (95.5%).

**What the measurement forced** (each found as wrong attachments): whole-block identity comes before position; position counts only without an identical-context rival; each anchor records evidence from its own version (how often its quote occurs, the best other context, its closest look-alike), which a match elsewhere must beat; context is the weaker of prefix and suffix similarity; fuzzy alignment counts only insertions and deletions. Amended 2026-10-09: a look-alike search cut off by its bound counts as indistinguishable (1.0), not as no look-alike. The 2026-10-15 rerun above includes that change; thresholds were unchanged. No audit PR changes anchoring or canonical rules, so PR5 does not rerun the corpus harnesses (ADR-23).

**When** (recorded 2026-10-15). A note's highlights and cards are resolved against its current version when its annotations are listed (`GET /api/documents/{id}/annotations`, which the reader calls on opening a note), not when a refresh finds the change. Only notes someone opens pay for it, and a refresh keeps its ceiling of 2 GitHub calls plus at most 128 move checks (amended 2026-10-22, from 8; see ADR-07) instead of one more per changed note with annotations. Each resolution is compare-and-set on the resolved version and the edit version, so concurrent listings, a reattachment or a user edit cannot be overwritten, and listing again changes nothing. The cost: listing the annotations of a changed note needs GitHub (503 `GITHUB_UNAVAILABLE` when it is down; the reader then shows the highlights saved on the phone), and the notebook shows a note's statuses as of the last time it was opened.

**Bounds.** Fuzzy matching is skipped for quotes over 1,000 characters, blocks over 20,000, or when more than 16 blocks share half the passage's words; the constructed worst case took 335 ms (389 ms in the 2026-10-15 rerun). Identical texts score 1 without the edit-distance table, which every stage would otherwise build even for an unchanged passage: a 10,000-unit one took 174 ms to resolve, now 0.3 ms (2026-10-17). Evidence is gathered for each highlight from the version's blocks, not from an index built once per version: the slowest of the 28,796 real cases took 13.8 ms, so an index would save milliseconds next to the GitHub fetch of that version.

**Consequences.** Some lightly edited short passages orphan. Any change to `Anchoring` is re-measured with `AnchorMeasurement` (ADR-23). Evidence on the phone (2026-10-07): an inserted paragraph re-anchored by block, a one-word edit by fuzzy match, a rewrite orphaned and was reattached, and a duplicated quote stayed on the original.

## ADR-07 — Document identity from complete snapshots

**Decision.** Each sync publishes one complete tree snapshot of the default branch in a transaction, instead of the original spec's incremental compare between commits. A path keeps its document; a document whose blob no other note has, before or after, reappears at exactly one never-used path moved; a vanished document with user data whose content is alike enough moved and was edited. Absent paths are marked deleted, never removed; an incomplete tree is a failure, never evidence of deletion.

- **Moved and edited** means Jaccard similarity of five-word shingles of canonical text at least 0.5, both versions with at least 50 shingles, and the pair the only one above 0.5 on both sides. It costs one blob read per candidate and is skipped when vanished documents plus new paths exceed 128 (8 before 2026-10-22, below). Measured with `MoveMeasurement`: the 38 real renames with edits scored 0.54–1.00, the most similar pair of different notes 0.198; block-text Dice was rejected (95th percentile 0.80).
- **Rerun and candidate ceiling** (amended 2026-10-22): on the grown repository (848 notes) the original method finds 39 real renames with edits, still at least 0.54, but the most similar pair of different notes (both with at least 50 shingles) is now 0.482: two templated `interview/00-orientation.md` notes. Thresholds were kept. Counting git renames down to 30% similarity (before, git's default 50% hid the most edited ones) adds three at 0.32–0.44 that the rule misses: two notes split into a folder and one renumbered and rewritten. Shingle containment (shared shingles over the smaller set) placed all 42 eligible real moves at 0.70 or above and different notes at 0.668 at most, a margin too thin on one repository to justify switching. Rendering is not the cost: median 1.5 ms, largest note (89 KB) 13 ms. The ceiling of 8 skipped nearly all real moves: at least 33 of the 39 came in reorganizing commits that alone added 56–70 paths. Against real GitHub, the 99 candidates of the largest such commit took 36–37 s read one at a time (the app waits 45 s), 9.1–9.5 s four at a time, 4.4–5.3 s at eight and 2.3–2.8 s at sixteen, about 330 ms per read at each, with no rate-limit refusal (`BlobReadMeasurement`, from the Mac, not the VM). The ceiling is now 128 candidates admitted in sets of 16: at most 8 rounds, the worst case of the 8 sequential reads before. One `RepositorySnapshotRefresh` owns admission, so overlapping refreshes cannot multiply the 16 reads in flight. The first failure other than an unavailable version interrupts its unfinished set and admits no later set, so a GitHub timeout is not followed by another round. GitHub advises against concurrent requests for one user; its secondary limit is 100 concurrent requests and 900 points a minute, and a refresh with candidates spends at most 130.
- **Concurrency** (amended 2026-10-09): GitHub is read before the connection row lock; under it, a sync that fetched before another sync published a different commit changes nothing (409 `SYNC_SUPERSEDED`). Every write that adds or changes a document's rows shares that lock. Amended 2026-10-17: so does connecting again, whose upsert locks the same row, and a sync whose default branch it changed meanwhile also changes nothing (409 `SYNC_SUPERSEDED`); before, such a sync published the old branch's snapshot. Owner and name are not compared: a rename or transfer keeps the GitHub repository id and its content.

**Consequences.** Branch rewinds reconcile like any other snapshot. Identical-content duplicates are never merged. Evidence: real path-only moves kept their ids (2026-10-07); a move with an edit kept its document and highlight.

## ADR-08 — Offline: a Room projection plus explicit pending changes

**Decision.** Room holds the server's complete lists and the latest rendered copy of each saved note, replaced only by complete responses. Local changes are rows marked pending and sent at the sync points (library open, note open, and a background sync after each local change; amended 2026-10-14, see below): reading state is last-write-wins by the client's time; a highlight or card creation and a grade carry a client mutation id the server makes idempotent; edits and deletes of acknowledged annotations are online with optimistic versions and visible conflicts.

- **Background sync** (amended 2026-10-14; before, nothing was sent until the next library or note open, and a **Sync now** menu action was the only retry): every local change (reading position, bookmark, highlight or card creation, offline delete, grade) asks WorkManager for one sync once the phone has a network connection, 5 s after the last change so a burst of reading saves becomes one run. It sends what waits with the same code library open uses, and stops there: each send saves the server's answer, and the complete lists are the screens' to load (amended 2026-10-17; before, every run also downloaded and rewrote every list, so each reading pause cost a request per repository plus four, and woke every observer of those tables). A change during a run replaces it (sending is idempotent), so the run cannot miss it. An unreachable server, a 5xx, or GitHub unavailable is tried again with exponential backoff from 30 s, at most 10 attempts (nine waits, about 4 hours 15 minutes; time without a network does not count); any other failure stops until the next change or library open. One sync at a time per process: sign-out and account deletion clear the phone under the same lock, and the background run sends nothing when nothing waits, so it cannot bring cleared data back. The Library shows how many highlights, cards, deletes, grades and bookmarks are unsent, with **Send changes** (amended 2026-10-22: reading positions are sent but no longer counted; every scroll saves one, so leaving a note showed "1 unsent change" until the background run 5 s later). The phone holds no other retry framework.

- **PhoneSync order** (amended 2026-10-09 and 2026-10-18): creations first (they need GitHub, so they wait when GitHub or access to it fails while the rest still runs), then grades, reading positions, bookmarks, and the library last. Only known item-refusal status/code pairs are marked final and allow the run to continue; a status alone is not a refusal. In particular, 422 `ANNOTATION_LIMIT` preserves a creation for after capacity is freed. Any other failure leaves unacknowledged work pending, with creation failures still allowing database-only passes when reachable.
- **Reading positions accepted** (amended 2026-10-19, audit PR3): the server clamps the client's time to [1970, server now] before last-write-wins storage, and stores any typed anchor within the existing request-body limit. NUL and unpaired-surrogate strings cannot round-trip through PostgreSQL exactly and are malformed input (400), not sanitized. A save makes zero GitHub calls. A successful response acknowledges the sent position and merges the server's time; a 404 for a note no longer owned acknowledges it so the next complete library can remove it. A malformed save stays loud and ends the sync; it is a programmer error, not a permanently refused item. If a malformed position remains pending, it stops bookmark sends queued behind it on every run; the sync does not silently acknowledge or skip it. Reading rows need only their existing pending flag; only bookmarks remain in the transient refusal list. Each pass sends each pending position at most once.
- **One library read, from one snapshot** (amended 2026-10-18; before, each read of the lists made 1 + repositories + 3 requests, each answered from its own server transaction and written as it arrived, so the phone could save lists from different server states, and a failure part-way left some replaced and some not): every read of the server's lists (library open, pull to refresh, **Send changes**, a repository's refresh on entry, **Check GitHub for updates** after its repository snapshot refresh, **Save all**, the count before a disconnect, and disconnecting a repository the server no longer has) is one `GET /api/library`: exactly 1 request and no GitHub call, however many repositories. `LibrarySnapshotReader` reads the repositories, every document of them, the reading states, the bookmarks and the notebook in one read-only `REPEATABLE READ` transaction, a fixed 6 queries however many repositories and notes: PostgreSQL answers every query from the snapshot the first one took, so a write committed during the read is wholly out of it and wholly in the next. It serializes one `LibrarySnapshot` answer and refuses one over 8 MiB (`LibrarySnapshotReader.MAX_RESPONSE_BYTES`) whole, before sending any of it (422 `LIBRARY_TOO_LARGE`); the app reads at most that same number, which its build takes from that line of `LibrarySnapshotReader.java`. The phone checks the whole answer, writes it in one Room transaction (`RepoReadDao.replaceFromServer`), and only after the commit sweeps the images of every version Room no longer holds a page of (ADR-22); a failed request or a broken answer writes nothing. Amended 2026-10-18: `GET /api/library` is the only list read. The five per-list routes (`GET /api/repositories`, `/api/repositories/{id}/documents`, `/api/reading-states`, `/api/bookmarks`, `/api/notebook`), which no app code had called since `/api/library`, are deleted with their response records, `Documents.list` and `Reviews`' own notebook snapshot, so `LibrarySnapshotReader` is the one owner of the read; every test that used them reads the library now. They had been kept for the release installed before `/api/library` (ADR-24); the snapshot-pinned image contract had already ended support for that release, so the deletion waited for no installation.
- **Deleting an unacknowledged creation** works offline (amended 2026-10-09, Room v8): it is marked `DELETING`, and the next sync replays the creation, then deletes it, so a late answer cannot bring it back. Since Room v11 (2026-10-15) a highlight's standing with the server is one state, `UNSENT`, `REFUSED`, `DELETING` or `ACKNOWLEDGED`, instead of three flags with impossible combinations.

**Consequences.** Offline creation never duplicates; changes reach the server without opening the library, usually seconds after the network returns, but Android may defer the run (Doze, app standby, Battery Saver) and a force-stop pauses it until the app is opened. On the Pixel, adaptive Battery Saver (on for most of 2026-10-14) holds the run until the app is opened, the phone charges, or RepoRead's battery usage is Unrestricted; offline edit of acknowledged annotations is not supported (Stage 3 scope decision). The library is one answer of at most 8 MiB, so a notebook too large for it holds back every list (422 `LIBRARY_TOO_LARGE`, shown as such), where before it was read last and only it failed (ADR-13's known limit). Evidence: an offline bookmark and reading save synced exactly once after reconnecting (Stage 2); a submission that arrived twice created one annotation, and a pending highlight survived a force-stop (Stage 3); a highlight and reading position saved in airplane mode reached the hosted server from a background run after the app was swiped away, once the job was not held by Battery Saver (2026-10-14); `LibraryTest` holds a write that commits while the library read waits between its queries, and the read lists none of it (under the default `READ COMMITTED` it listed the write's reading state without its note), and the next read lists all of it; a library one byte over the cap was served before the cap and is refused whole after it, and one exactly at it is served (2026-10-18). `PhoneSyncTest.aLibraryRequestThatFailsLeavesEverySavedListAndImageAsItWas` passes on the phone with the rest of the device suite (75 tests, 2026-10-18).

## ADR-09 — "Changed since last read" compares the version actually read, by source lines

**Retired 2026-10-19 (audit PR1).** Each note is final to its author, who does not mind rereading. Section change summaries, their backend route and comparison code, and the phone-only baselines and acknowledgement are deleted. Room v15 drops only `change_baselines`, preserving saved pages and user-owned work. The library's recently changed/updated-since-read lists still compare document and reading versions; no summary is fetched. Historical decisions and evidence remain in git.

## ADR-10 — Search is local substring matching over what the phone has saved

**Decision** (Stage 6). Search runs on the phone over note titles and paths in the saved lists, the canonical text of saved notes (sent with each note), and highlights — SQLite `LIKE` with escaped wildcards, no full-text index or server search. Ending a session preserves the phone's saved data. Signing in as another account is allowed, replaces acknowledged lists on sync and can send older pending work under that account: the accepted one-account limit in ADR-22 (amended 2026-10-19; the earlier account-mismatch rejection is retired).

Amended 2026-10-18 (superseded for body results by the 2026-10-21 block decision below): one query returns one row per matching note before the 50-note limit, named by its `documents` row (current title and path), with its saved text when that matched; a note removed from its repository matches while its saved copy is kept. Before, listed and saved rows were unioned, limited, then de-duplicated in Kotlin, so 60 matching notes showed as 25–26 and a copy saved before a rename was listed by its old name.

Amended 2026-10-21: the content response carries each canonical search block as `{id, text}` instead of flattening every block into one newline-delimited string. Room v17 stores those rows in `note_search_blocks` and removes `notes.searchText`; its migration reconstructs existing rows from the same saved HTML `data-block-id` and `data-anchor-text` attributes the reader uses. A body result carries its saved blob SHA, server-issued block ID and exact UTF-16 text range. Tapping it draws that range through the reader's one highlight pipeline and reveals it before the WebView becomes visible; if the page changed between search and open, the reader refuses to reuse the range in another version and asks the user to search the current note again. While that hidden WebView finishes positioning, the reader says `Opening note…` instead of showing a blank region or flashing the wrong position. Title/path results remain explicitly labelled and open normally. Highlight and annotation matches open their exact passage. There is no line-number-to-block-ID reconstruction and no parallel flattened search path.

Amended 2026-10-21: one note contributes only its first matching canonical block, in document order, before the existing 50-body-result limit, so a repetitive note cannot crowd out other notes. Further occurrences belong to **Find in note**: the reader scans the displayed page's canonical block text literally and case-insensitively, reports the count, highlights only the active occurrence through the same highlight pipeline, and wraps Previous/Next. Each operation scans at most the saved page's existing 2 MiB ceiling, retains one occurrence and makes zero external calls.

**Consequences.** Notes not saved on the phone match by title only; since ADR-19 every note can be saved. Non-ASCII letters match case-sensitively. Adequate for one person's repository; revisit with FTS if it is slow or too literal.

## ADR-11 — Disconnecting deletes everything stored for that repository; account deletion deletes everything

**Decision** (Stage 6). Disconnect deletes, in one transaction under the sync lock, the connection, its documents, and the user's reading states, bookmarks, and highlights (whose quotes are repository content) on them; the phone removes its copies including unsent changes. Account deletion does that for every connection, plus sessions, sign-in codes, mutation records, the user, and the stored GitHub token. Disconnect makes no GitHub call; the App stays installed until the user removes it on GitHub. Account deletion also revokes RepoRead's GitHub authorization for the user, as signing out of the last device does (amended 2026-10-13, ADR-03; at most 2 GitHub calls, and a failed revocation does not stop the deletion). It revokes only after the deletion has committed, with the token read before the deletion removed it (amended 2026-10-15: revoking first meant a deletion that then failed left the account in place with its GitHub authorization gone, which cannot be undone). Amended 2026-10-19 (audit PR2): account deletion clears the server, ends the session on confirmation and keeps the phone's notes and pending work. Its dialog says so. Disconnect still removes its local copy. The 2026-10-18 decision that account deletion also cleared the phone is superseded. Copies already in the server's database backups stay until those backups are replaced (on the VM the newest 14 nightly and 14 deploy dumps, on the developer's Mac the newest 30), and dumps taken by hand before a migration are kept until deleted by hand ([backend/README.md](../backend/README.md), Backups). Both dialogs say so, without repeating the numbers `backend/deploy` owns; the phone's own data is in no backup (ADR-22). Before, the dialogs said only that the deletion cannot be undone.

**Consequences.** Reconnecting after a disconnect starts fresh; its deleted local copy is not recoverable in the app, though restoring a server backup can bring server rows back. Account deletion keeps the phone's notes (audit PR2). Upstream note deletion is different: it keeps history (ADR-07). The phone syncs before counting what a disconnect will delete. Evidence (2026-10-07): a throwaway repository's disconnect removed exactly its rows on both sides; account deletion emptied every user table and the phone, then a dump was restored.

## ADR-12 — Personal distribution: one signing key, backend over adb reverse

**Decision** (Stage 6). Every build is signed with one personal key kept outside the repository, so each release installs over the last. The debug build is a separate app beside it: `com.reporead.android.dev`, named RepoRead Dev, with its own data. The hosted server sends the release app its sign-in code through a verified App Link, `/app/signed-in`, whose `.well-known/assetlinks.json` names the app's package and signing certificate, so no other app can claim it; the Mac's backend sends the debug app its code on `reporead-dev://auth`, as a loopback address has no domain to verify (amended 2026-10-17: the code went to a custom scheme, which any app can register and then start its own sign-in to receive, and PKCE stops a code being injected, not that; amended 2026-10-15: debug builds shared the release's app id and installed over it, so testing on the phone replaced the app in use, and putting back an older release over a newer debug build's database left it crashing on launch). The release build's backend address is superseded by ADR-14; debug builds keep the loopback backend reached through `adb reverse`. No Google Play.

**Consequences.** Losing the key means uninstalling to update. Since ADR-15 a copy is also a GitHub secret, of the `production` environment, which only `main` may use. The release app's data on the phone cannot be inspected: it is not debuggable, and the debug app has its own database, signed in against the Mac's backend. Android verifies the link when the app is installed, so the server must serve `assetlinks.json` before a release is installed (`adb shell pm get-app-links com.reporead.android` shows the result), and CI checks each APK's certificate against that file. A release from before the App Link waits for its code at `reporead://`, which the server no longer sends, so its new sign-ins stop at the server's page until Obtainium updates it; an existing sign-in keeps working.

## ADR-13 — Anchored cards; server review log, phone-only scheduling

**Decision** (P4, 2026-10-09). CARD annotations reuse highlight anchors, re-anchoring, orphaning and idempotent offline creation. The question is an interview-bank question whose answer is its authored `Canonical answer` line (amended 2026-10-13, ADR-20; before, a P3 prompt needed an answer passage the developer selected). Amended 2026-10-21 (user decision): the reader no longer makes cards. Its **Make a question** (on a selection or a highlight) was never used, and only those cards needed confirming in a new version, so it was deleted with the confirmation it required. The server owns the immutable review log; the phone owns the one pure scheduler over the log and the session size (`SESSION_LIMIT`, 40; amended 2026-10-23) so offline grading and review work. No scheduler dependency, persisted due dates, AI, inferred answers, or GitHub writes; grades are sent by the sync that sends every local change (ADR-08; amended 2026-10-14, when grades waited for Library sync).

**Scheduling** (amended 2026-10-15: a fixed ladder replaced SM-2, whose gaps were hard to predict — Hard, Good and Easy all gave 1 then 6 days, and later gaps were the previous one times a hidden ease that every past grade moved). Grades are stored as Again 0, Hard 3, Good 4, Easy 5; below 3 is Again, decided in one place on the phone (`isMiss`, amended 2026-10-17). The gaps are the steps 1, 3, 7, 14, 30, 60, 120 days: Again returns a card to the first step, Hard steps back one (not below the first), Good climbs one and Easy two, capped at the last (Hard amended 2026-10-23, user decision: before, it kept its step); a new card starts on the first step, so its first grade gives Hard 1, Good 3 and Easy 7 days (amended 2026-10-21, user decision: before, it started one below the first, so Hard and Good both gave 1 day and Easy 3). Each grade button shows the gap it would schedule. A card is due from the start of the phone's local day its gap ends on. In a session, a card graded Again comes back later in the same session, unsaved, until answered right; Hard is still a pass, so it leaves the session, but its saved grade steps the schedule back one (amended 2026-10-15; from 2026-10-14 anything below Good came back, and before that each card appeared once). The schedule is derived from the immutable log, so each change reinterprets existing grades with no data change: on 2026-10-21 a card whose first grade was Good became due 2 days later than before, and from 2026-10-23 each Hard above the first step shortens its next gap by one rung. Cost: the ladder reacts only to a card's current step, not its whole history. No scheduler dependency; consider FSRS only if review data shows a need.

**Safety** (amended 2026-10-21, user decision). A card is graded only in its bank's current version as saved on the phone, and only while that version still asks its Canonical line: Review reads the card's question, answer and version from the saved bank (`reviewQuestion`, matching the card's drawn Canonical text, as Practice's `scheduledLines` does), and the grade carries that version. `RepoReadDao.recordReview` saves it only while that version is still the note's current, saved one, so a bank refreshed while answering saves nothing. A card whose line is no longer in the bank shows its saved prompt and offers the bank, where the server re-anchors it (an edited line can keep its card) or the developer deletes it; it is not graded. Before, every known version change of the note blocked its cards until the server had placed the card in the new version (only on opening the note) and the developer confirmed **Answer is still right** online; the server refused any other grade (409 `CARD_CHANGED`). The question and answer are authored together in the bank, so the confirmation asked nothing the bank did not already say, and a change anywhere in a bank blocked every card in it. The server records any grade of the user's card, keeping its version (`blobSha`): only the phone reads the bank. An identical already-committed replay remains successful. Grade writes use client UUIDs and take the connection lock in shared mode, like every write to a document: a refresh or disconnect waits for them, and writes to other notes and cards of the repository do not. Offline review cannot know about edits that have not been refreshed. The phone's rule has one owner, `AnnotationEntity.cardBlock` (refused, note removed, current version not saved), whose first reason that applies is the one Review offers a fix for; Review adds `CardBlock.NOT_ASKED` when the saved bank has no question with the card's line. A card the server refused is on no schedule, so Practice asks its question again. The server column `annotations.checked_blob_sha` was dropped by V16 in the release after the one that stopped using it (ADR-24); Room v18 dropped the phone's copy.

**Practice persistence** (amended 2026-10-19, audit PR4). `RepoReadDao.saveCardWithFirstReview` owns bank-version and existing-card admission inside its write transaction, under `PhoneSync.committed`. The transaction inserts the card and its first immutable grade in one Room transaction; an insert failure propagates and rolls back both, with no card-only fallback. Only a completed pair notifies background sync, once. A concurrent or restored submission for a Canonical line already on this phone's schedule writes nothing. This operation makes zero external calls. No schema change or migration is needed: identity uses the existing document id and drawn Canonical text; existing cards and the scheduler are unchanged. Only the bank's Canonical line is confirmed, not the supplementary section linked from it (ADR-20).

**Shared phone rules** (2026-10-19, audit PR4 review corrected during PR5). `QueryResults.kt` owns schedule eligibility (`reviewable`) and the scheduled document/drawn-Canonical-line keys (`scheduledLines`), used by Practice and the DAO. `RepoReadDao` owns both grade-admission decisions in the same SQLite transaction as their writes: Practice checks the current saved bank and existing schedule, and Review checks the current card and answer. PhoneSync only orders and commits operations, while the scheduler owns grade buttons and ladder behavior. The server clamps reviewedAt to [1970, server now] and V15 retains the original client timestamp for immutable replay checks; a changed payload still gives `MUTATION_ID_REUSED`, and a refused grade remains visible and excluded from scheduling.

**Session size and grade range** (amended 2026-10-23, user decision). The session size is a constant of the phone, `SESSION_LIMIT` in `ReviewSchedule.kt`. It was the server's `sessionLimit`: sent in every library answer, kept in Room's `review_limits`, and never enforced by the server, which does not refuse a grade for it (a refused grade can only discard a review already done). The phone builds sessions, offline too, so it owns their size; the knob was a runtime value where a constant suffices. Room v19 drops `review_limits` (`DropReviewLimits`), and Review no longer waits for a library answer before it can start. The grade range, 0 to 5, is checked only by the server: `ReviewController` answers 400 `INVALID_REVIEW` and `review_log.grade` has a `CHECK` (V7). The phone's second check (`saveReview`, `InvalidReviewGrade`, and `INVALID_RESPONSE` for a bad grade in a snapshot) is deleted, so a grade the server refuses comes back as an ordinary item refusal. Contract step (ADR-24): the server keeps sending `sessionLimit` while a release that reads it is supported; remove it from `Reviews.Notebook`, `backend/openapi.json` and their tests once the release with this change is installed.

**Outlook ownership (2026-10-20).** `rememberReviewOutlook` owns the midnight/time-zone-aware outlook for Library, Practice and an empty Review completion. Dismissing refused grades is a local mutation under `PhoneSync.committed`, so leaving a screen while it waits for the lock cannot lose the dismissal.

**Data controls.** ADR-11 includes cards and review logs. Card deletion cascades its grades, disconnect removes the repository's cards/logs and phone copies (pending work included), and account deletion removes everything on the server, keeping phone data (audit PR2, ADR-22). Amended 2026-10-19 (audit PR1): Notebook Markdown export is retired because it was never used; its writer, sharing provider, UI and tests are deleted.

**Known limits** (recorded, not fixed). The notebook is not paged: it is part of `GET /api/library` (ADR-08, since 2026-10-18), and past about 40,000 grades that answer exceeds the server's 8 MiB cap and is refused (422 `LIBRARY_TOO_LARGE`), so no list loads (decided 2026-10-09: record the limit, page later). A card's question cannot be edited; delete and recreate it.

**Evidence.** Fixture device tests passed twice (23 tests) without real-account cards. The two-week real-review exit gate is pending.

## ADR-14 — Hosted backend on an Oracle Cloud Always Free VM; debug builds stay on the Mac

**Decision** (2026-10-13). The release build talks to `https://reporead.duckdns.org`, an Oracle Cloud Always Free `VM.Standard.A1.Flex` (1 OCPU / 6 GB, home region `ap-singapore-1`) running the same backend and PostgreSQL 17.11, behind Caddy with a Let's Encrypt certificate. Debug builds keep `http://127.0.0.1:8081` through `adb reverse` for testing unmerged changes. The server still binds only to `127.0.0.1`; `REPOREAD_PUBLIC_URL` fixes the OAuth callback (never the request's `Host`), and forwarded headers are honoured from loopback so redirects and the session cookie stay on HTTPS. The Mac's database moves to the VM at switch-over so phone and server ids keep matching.

**Why this host.** Free hosts that sleep (Render, Koyeb) restart often and Render deletes free databases; Fly.io and Railway have no free tier; Google's e2-micro has 1 GB for the JVM and database together. DuckDNS is free and on the Public Suffix List, so Let's Encrypt limits are not shared (sslip.io and nip.io are not listed).

**Consequences.** Refresh and sync work wherever the phone has internet. The backend is reachable from the internet for the first time; only Caddy (80/443) and SSH are open. Oracle may reclaim an Always Free VM idle for 7 days (CPU, network and memory all under 20%); RepoRead alone used ~16% of memory, so the backend commits a 1 GB heap at startup (`-Xms1g -XX:+AlwaysPreTouch` in its systemd unit), keeping memory near 33%. Oracle may also change free limits (halved in mid-2026). DuckDNS is a small volunteer service; losing the name means a new address and an app rebuild. The database is dumped nightly on the VM and the developer's Mac copies the newest dump each evening (since 2026-10-15; backend README, Hosted VM), so losing the VM loses at most the changes since the last copy; the copies quote private notes and stay on that Mac. Pushes to `main` that touch the backend deploy through GitHub Actions with a key that can only run the VM's deploy script, held only by a job that runs no third-party code (tests and the build run in jobs of their own) and stored as a secret of the `production` environment, which only `main` may use (both amended 2026-10-17), which dumps the database before the restart and fails the run if the new jar is not healthy. It does not put the previous jar back: the new one may already have migrated the schema, which the previous one cannot run on, so going back is by hand (ADR-24; amended 2026-10-17, when the script stopped restoring the previous jar itself). The scripts themselves are installed by hand, since a CI that could replace them would hold root on the VM (a check that failed the run when they differed was removed the day it was added, 2026-10-17: its pipe hid the deploy's own failure). The way back, `backend.previous.jar`, is copied only from a backend that answers its health check, so a failed deploy never replaces it (amended 2026-10-17).

## ADR-15 — App releases through GitHub Releases, installed by Obtainium

**Decision** (2026-10-14). Pushes to `main` that change the app build a release APK in GitHub Actions, signed with the personal key (ADR-12) from secrets of the `production` environment, and publish it as GitHub Release `v0.1.<commit count>`. Obtainium on the phone installs each release over the current app. `versionCode` is the commit count of `HEAD`, which only grows along `main`. The tests run in a job without secrets; the release job holds the key while Gradle builds and signs, because the build refuses to package an unsigned APK so that no build is ever signed by another key. No Play Store: its internal testing track would also work, but needs a paid developer account, Play App Signing and a service account.

**Safety.** The workflow refuses to publish an APK whose signing certificate is not the personal key's (`2049299f…53293f`). Pull requests run unit tests, the reader's syntax check and bundle (`:app:mergeDebugAssets`, the packaged app's asset wiring), and compile the device tests, without secrets; only the release job on `main` can write releases. Amended 2026-10-19: the key and its password were repository secrets, which a workflow on any branch can read; they are now environment secrets of `production`, which only `main` may use, so only the release job on `main` can read them, as with the backend's deploy key. Amended 2026-10-18: before, a `reader.js` syntax error passed pull-request CI, since compiling the device tests merges no assets; and the workflow now also runs on `LibrarySnapshotReader.java`, whose size cap the build parses, and `assetlinks.json`, which the release check reads, so a backend-only edit cannot break Android builds unseen.

**Consequences.** App updates no longer need the Mac or adb. The signing key now also lives in GitHub: anyone who controls the repository's Actions or secrets can publish an update the phone accepts as genuine, so the GitHub account is now part of the app's trust boundary. The repository is public, so release APKs are downloadable by anyone; they contain nothing beyond the public backend address. A hand-installed branch build with a higher commit count blocks the next release until it is reinstalled with `adb install -r -d`.

## ADR-16 — A read-only GitHub App; the user's own token decides what can be connected

**Context.** A personal access token would be broad and long-lived. An App installation token proves only that the App can read a repository, not that the signed-in user may.

**Decision.**

- RepoRead is a GitHub App installed on repositories the user chooses, with repository contents and metadata read-only.
- Every read uses the signed-in user's user-to-server token. A repository can be connected only when GitHub lists it for both that user and an installation; connecting re-checks it. No installation tokens are used.
- The App's client secret is a single token in a regular, non-symlink, mode-0600 file of at most 4 KiB outside any Git repository. Missing or unsafe configuration fails startup; no credential is in source.
- A repository is refreshed from GitHub only when the user taps refresh: no webhooks, no refresh on app open, no polling.
- **Who may sign in** (amended 2026-10-15). GitHub decides which repositories a user can connect, not who may use the server. The App is public and the hosted backend is on the internet (ADR-14), so before this any GitHub user could sign in, have their GitHub token stored here, and use the VM and the App's rate limits. The server now serves only the GitHub user ids in `REPOREAD_ALLOWED_GITHUB_USER_IDS`: anyone else's sign-in fails before a user or token is stored, and a session of someone removed from the list is refused. It is configuration, not code, because the list changes without a release (for example to let someone try the hosted app). A GitHub login can also start only from the app's `/app/sign-in`, so no login reaches the callback without the app's PKCE challenge.
- **What a stranger can make the server keep** (amended 2026-10-15). Only the browser session `/app/sign-in` opens to hold the app's challenge through GitHub's sign-in: it lasts 5 minutes, at most 100 exist at once (more sign-ins get 503 `SIGN_IN_BUSY`), and a refused browser request opens none; any request's body is read only up to 256 KiB, before anything parses it, and form and multipart bodies, which no route takes, are never parsed (both 2026-10-17). Every route on the browser chain is a GET, so it has no CSRF protection, whose token opened a session for each refused POST until 2026-10-17. Before, sessions lasted 30 minutes without a cap, and any refused browser request also opened one, so a flood of requests could exhaust the server's memory; now it can only delay sign-in. There is no per-client rate limit: Caddy's standard build has none, and without a session nothing else is reachable.

**Consequences.** GitHub's permissions decide eligibility; the allow-list decides who can use the server at all. Edits on GitHub appear on the phone only after a refresh, and change indicators depend on the phone's saved note lists. Evidence: on 2026-10-02 the user-token eligibility check returned the private notes repository; the first real sync (2026-10-06) found 641 Markdown documents within its call ceiling.

## ADR-17 — Highlights and cards share the annotations table; bookmarks have their own

**Decision.** `annotations.type` is `HIGHLIGHT` or `CARD`. A highlight's optional note is its textual annotation (no separate annotation type); there is no colour; deleting removes the row (no deleted status), while its mutation record stays so a late replay is refused with 410. A bookmark is one row per user and document in `bookmarks`, owned by `Bookmarks` (amended 2026-10-22, user decision: until V17 a bookmark was a third type, `BOOKMARK`, in `annotations`).

**Why.** Highlights and cards are both anchored passages: an original anchor, a current location, re-anchoring, orphaning, idempotent creation by mutation id and one capacity. A bookmark has none of these; it is document-level state like a reading state, and the phone already kept it in its own table. The reason bookmarks once shared the table, one owner for the user's state on a document, did not hold: reading states were already their own table, move detection (ADR-07) and disconnect (ADR-11) already read both, and every query of `annotations` filtered bookmarks back out by type.

**Consequences.** Move detection counts a reading state, a bookmark or an annotation as user data. `annotations` names its rows loosely: a card is a question anchored to a bank line (ADR-13), not a note on the text; renaming the table is not decided. `BOOKMARK` left `Annotations.Type` and the published API, which never sent it, so the app's guard against it is gone.

**Moving the rows (2026-10-22, ADR-24).** V17 creates `bookmarks` and moves the rows, so no bookmark has two. Its foreign keys cascade from `users` and `documents`, so the previous release, which does not know the table, can still disconnect a repository or delete an account. The previous release runs on this schema but lists no bookmarks, and a bookmark it sets lands in `annotations` as `BOOKMARK`. This release does not list that bookmark until the contract step moves it: every `Annotations` query names `HIGHLIGHT` and `CARD`, and disconnect counts what it deletes by type in SQL, so such a row goes with its repository instead of failing on an unknown `Annotations.Type`. The contract step, owed now that this release is deployed (the backend deploy of 2026-10-22 passed its health check, feature list): move any remaining `BOOKMARK` rows into `bookmarks`, remove `BOOKMARK` from `annotations_type_check`, drop `annotations_one_bookmark_per_document`, and delete the type filters in `Annotations` that only exclude `BOOKMARK`.

**Capacity (2026-10-20, user-approved).** `Annotations` admits at most 500 combined highlights/cards per document and 5,000 per user; bookmarks are not annotations and do not count. A new creation locks the user row (`FOR NO KEY UPDATE`) before the connection, then checks both counts in its insertion transaction after replay detection. This orders admission across repositories without a new lock registry or schema. At capacity it returns 422 `ANNOTATION_LIMIT`, rolling back the mutation claim; exact replays, edits and deletions still work, and pre-existing rows above a ceiling are not removed. The phone leaves a capped creation at the head of the pending queue: later creations and their grades wait, and each sync revalidates the same creation with one GitHub blob call until existing annotations are deleted to free capacity. Grades for acknowledged cards and reading/bookmark sends can still proceed. At most one blob call still precedes a new creation; replays need none. The counts are chosen policy, not measured capacity, and do not replace the independent 8 MiB library limit or bound the accumulated review log.

**One highlight per phrase (2026-10-22, user decision).** A phrase has at most one highlight, and everything written about it goes in that highlight's note; a second highlight on the same text would only split the notes and spend capacity. A phrase is a block of one version and its offsets, compared exactly with where each highlight is drawn (the server's location, or the original selection while the creation is pending). The page's selection capture leaves out leading and trailing whitespace (ADR-05), so a selection with or without the space after a word is already the same phrase when it reaches the phone; nothing compares modulo whitespace. Highlights that overlap without being the same phrase stay separate. A refused highlight marks no phrase: it is never sent again, so the user can highlight that text again and the new one is sent. The phone owns the rule: `RepoReadDao.saveLocalAnnotation` checks and writes in one Room transaction, so two saves of one phrase cannot both pass, and returns the highlight already there. Highlight then says the passage is already highlighted; Add note opens that highlight's note editor, or, while its creation is unsent, says its note can be edited once the server accepts it. The server does not check: it would have to refuse an offline creation after the fact, and the phone already holds the highlights of the note being read. Not covered: highlights made on two devices, Reattach onto a phrase another highlight marks, re-anchoring that moves two highlights onto one phrase, and highlights saved before this rule, which stay as they are; one saved then with surrounding whitespace does not match a later selection of its text.

## ADR-18 — Rendering changes never change an unchanged blob's canonical text

**Context.** Anchors are offsets into canonical text (ADR-05); changing the text of an unchanged blob breaks every anchor in it.

**Decision.**

- Features that change how a note looks are applied after parsing, keeping their source text in the block but hidden (`.wl-hidden`), or are placed outside `[data-block-id]`: Obsidian `[[links]]` and `![[embeds]]`, footnotes, code-block tools, the LeetCode study view (CSS only), and an answer page showing one section (layout only).
- **Footnotes** are marked after rendering, without `commonmark-ext-footnotes` (P1, 2026-10-07). The extension splits and moves consecutive definitions, which CommonMark otherwise keeps as one paragraph; the notes have 233 definitions, 190 of them directly after another. A definition whose text is just a URL, which CommonMark reads as a link reference definition, is escaped before parsing so it stays text like the rest (2026-10-17); so is a leading byte order mark dropped, which would make a first heading text.
- The page reaches native code only through same-origin links the app intercepts (`/note-link`, `/copy-code`) and native `evaluateJavascript`, all through one boundary (`ReaderPage.kt`) returning decoded JSON values (outline, position and missing-highlight arrays are not stringified and parsed again) that raises a page script's own error with the expression, since WebView reports a script that throws as null (2026-10-17); never a JavaScript bridge. Only the renderer and the page's own script make such links: an authored link to the app's origin, or a relative one that is not a note in the repository, keeps its text and opens nothing (2026-10-17), so the app never reads a link it did not write.
- When saved pages must be fetched again, `MarkdownRenderer.FORMAT` is bumped (now 4); the phone refetches a saved copy of an older format when it opens the note online. A format-only outdated current version still opens without a warning offline; a failed fetch of a newer version keeps the saved copy with the failure reason.

**Consequences.** Rendering the whole notes repository before and after footnotes gave identical canonical blocks for all 653 renderable notes (`RenderedCorpus`, 2026-10-07); before and after the escaped definitions, the byte order mark and the link rule, identical blocks for all 799 (2026-10-17), with 31 pages changed only by links to files and folders that no longer look tappable. The format was not bumped for the 500-character heading cap (2026-10-09), so an older saved copy can still send a longer heading, which the server refuses as a reading position until the copy is refetched.

Amended 2026-10-19 (audit PR1): the unused full-screen figure and its links/layout are retired. Tables and diagrams keep their in-page sideways scrolling. Change-summary-only source-line metadata is removed from the renderer; block numbering, canonical text and heading paths are unchanged. No format bump or canonical-rule change is part of this deletion.

Amended 2026-10-19 (audit PR3): format **4** records the heading-path cap, BOM handling and URL-only-footnote presentation already shipped; the app derives `BuildConfig.RENDER_FORMAT` from `MarkdownRenderer.FORMAT` during its build, with no hand-copied constant or literal-value alignment tests; the missing bump above is paid, and reading anchors no longer have that length restriction. No rendering or canonical-rule changes accompany the bump; existing canonical-block and heading fixtures stay unchanged. Room **v16** retires only cached pages whose `length(cast(html as blob)) + coalesce(length(cast(searchText as blob)), 0)` reaches 2,097,152 UTF-8 bytes, without loading them into a CursorWindow. Their derived note links are removed explicitly in the migration (Room enables foreign keys afterwards), and the existing startup image sweep removes their images. All user-owned rows and smaller pages survive. PR1/PR2 already shipped v15, so its migration is preserved and both v14→v16 and v15→v16 are covered, rather than editing an applied migration. No renderer-migration registry is introduced.

## ADR-19 — Every note can be saved on the phone, one note at a time, with no eviction

**Decision** (P2, 2026-10-07). This reverses the build plan's "do not download the whole repository". **Save all notes on this phone** fetches every note whose saved copy is missing, of another version, or of an older page format through the existing `GET /api/documents/{id}/content`, one at a time, so bodies stay off the server (ADR-02) and later runs fetch only what changed. Not the repository archive: it redirects to another host, exceeds the 1 MiB response limit, and carries files that are not notes. Every saved note is kept; eviction waits until storage matters. Link previews (opened by a tap, because a long press selects text) and **Linked from** backlinks are computed on the phone from saved copies, because the server keeps no bodies.

Amended 2026-10-18: Save all is WorkManager work, unique per repository (needs a network; asking again while one waits or runs changes nothing), so it runs whether or not any screen is open. WorkManager owns the run, and the folder screens show what it reports: waiting, progress, or the last outcome. While a run waits or runs, the repository menu offers **Stop saving notes**: it awaits cancellation, keeps every complete saved page, and releases the repository controls, so a long backoff never requires signing out to disconnect. Before, it ran in the folder screen's coroutine scope, so leaving the screen stopped it. A run Android stops part-way (ordinary background work is stopped after about 10 minutes, and when the network goes) is started again, and each run fetches only the notes not yet saved, so nothing records where it stopped. Failures are tried again as the background sync's are (ADR-08); WorkManager counts every start as an attempt, including one after Android stopped the run. The outcome counts the notes the server refuses instead of naming them, because WorkManager caps a run's output at 10 KiB; opening one says why. Failure display text is bounded too: at most `Data.MAX_DATA_BYTES / 4` UTF-16 units plus an ellipsis when shortened, leaving room for the encoding and progress fields even with multibyte text. This bounds only the persisted display text, not the server response. The worker enters the process's one `PhoneSync` directly, like background sync (audit PR2, 2026-10-19). Account operations neither gate it nor cancel or prune its work; signed-out HTTP calls follow the existing non-retryable session failure path. Repository-level Stop still awaits cancellation. The previous Account removal/cancellation ordering is retired (ADR-22).

Amended 2026-10-20: Save all also checks each listed page's images, including already-current saved pages (user decision), through `NoteImages` and its existing snapshot-keyed cache. It reads and parses one page at a time, then tries each distinct `/repo-image/` path once, sequentially, before reporting that page's progress. The server's existing 64-reference limit bounds image calls; cached images make none. One run makes at most one library call, one content call per outdated note and 64 image calls per saved page. No new table, dependency or retry mechanism. Unknown legacy snapshots never fetch images. Save all uses `NoteImages`' throwing fetch, not the WebView's unavailable-image policy. Its one per-page catch in `PhoneSync` counts 422 `UNSUPPORTED_CONTENT`, 404 `IMAGE_NOT_FOUND` and 400 `INVALID_IMAGE_PATH` as skipped pages: stop that page's image pass, preserve its text, count it once (not also fetched/already saved), and continue at the next page (user confirmation, 2026-10-20). Every other image API failure ends the run and reaches the existing worker boundary exactly as a content failure does: 5xx/unreachable retries within the worker's existing limit, while 401 stops with a sign-in reason after Api ends the refused session. No later image is requested in that run. Only the WebView-facing `image()` catches API failures as unavailable; no failed call starts a fallback strategy. Progress counts all listed pages checked; completion counts pages fetched/already saved/skipped, not guaranteed image availability. Cancellation is checked between images; the current blocking request can finish within Api's existing timeouts, and complete files survive. Prefetch uses PhoneSync's existing per-page lock to order it against replacement/disconnect; `openNote` and every `committed` write can queue behind the current page's one content call plus up to 64 image calls, rather than the one content call they previously waited for. WebView image reads remain outside that lock. No image-file lock is held during HTTP. Cleanup amendment (2026-10-20): fetched opens sweep after their page, while Save all sweeps replaced images once under cancellable `locked` only after a successful loop; failure/cancellation defer cleanup to the next library refresh, Library open or startup. Its initial library refresh still sweeps forgotten pages. The per-page skip table remains distinct from mutation refusal because it answers which failures are permanent after a fresh library read.

**Consequences.** Before images were included, a first run cost one GitHub call per note (654 notes took 5 min 43 s); a repeat cost none. 653 saved notes took 28.8 MB on the Pixel. These historical measurements exclude image prefetch. A note the server refuses (over 4,096 blocks) is never saved and is asked for again on each run. Like the background sync, Save all may wait while RepoRead is off screen when Android restricts background work (adaptive Battery Saver, unless RepoRead's battery use is Unrestricted). Checked on the Pixel on 2026-10-18 (RepoRead Dev, Mac backend, the 800-note repository, adaptive Battery Saver on). A run kept going after leaving the folder screen and the app. After a forced job timeout (`cmd jobscheduler timeout`), it started again fetching only the missing notes (521 of 650 left). With battery use Optimized, a run restarted in the background stalled when Android froze the cached process; reopening the app resumed it, its interrupted request failed as unreachable, and it was tried again 30 s later. With battery use Unrestricted, the restarted run finished in the background: 799 of 800 notes saved, and the 4,096-block note was counted, with opening it giving the reason. Historically, before audit PR2, a sign-out during a run cancelled it after the note in flight; the server received nothing more, Room was empty, and after signing in again the folder showed no outcome. Repeated after the worker moved behind `Account` (PR #66): a run kept going with the launcher in front, a sign-out mid-run cancelled it, the server rendered no note after revoking the session, and Room was empty. With every note saved, work over saved pages must be bounded ([invariants](invariants.md#bounded-memory-on-the-phone)): **Linked from** reads only the note links kept with each saved page (`note_links`, written when the page is saved), never the pages (amended 2026-10-15; before, it read every linking page 25 at a time, which took 3.2–3.7 s, and reading all 422 at once had taken the heap from 8 MB to about 67 MB). With the backend unreachable, a never-opened note opened and was found by a word in its body (exit gate passed 2026-10-07).

Amended 2026-10-20 (performance PR1): a saved page is current when its blob and path match the listed note and its render format is current. The repository commit must also match only when the saved HTML contains `/repo-image/` or `image-blocked`: those pages depend on snapshot-bound image contents or embed resolution, including a missing image added later. Their snapshot must be known; an unknown legacy snapshot still requires a fetch. Text-only pages remain current across commit-only changes, even with unknown legacy snapshot metadata, and keep their saved snapshot rather than being relabelled. `PhoneSync.sameVersion` derives this rule from the `SavedPageEntity` both Save all and `openNote` already read; no schema, API, query, concurrency or call-limit change. Format upgrades still fetch text-only pages. This narrows the commit-wide invalidation introduced for snapshot-consistent images without weakening image identity or changing the existing stale-copy failure policy. A full first save remains sequential; real-account one-note timing after this change is not yet measured.

## ADR-20 — Practise from interview banks, in sessions that show the linked answer

**Context.** Practice testing and spacing beat highlighting and rereading for retention, and rereading makes learners overconfident (Dunlosky et al. 2013; Roediger & Karpicke 2006). P3 (2026-10-09) first drew questions from core notes' own `Questions this file answers` and `Review and practice` sections. Interview banks were added next: an `interview/` folder beside a topic's notes, whose questions each carry a `Canonical answer:` line linking the core section that answers them ("the note owns every technical answer").

**Decision** (2026-10-13 and 2026-10-14).

- **Source.** Questions come only from notes in a folder named `interview`; core notes' own question sections are not a source anywhere. Practice lists only folders holding an interview folder.
- **Recognition** keys on each question's `Canonical answer`/`Canonical path` line, not on section names or numbering; a heading without exactly one (questions written as H4s under one H3 give several), a line under no H3, or a later prompt repeating a Canonical line, is listed as a non-question, never silently dropped (amended 2026-10-17: before, the first of several lines answered the H3 and a line under no H3 vanished). A `Canonical path` group is one question: its heading, then its top-level list items numbered in bank order (amended 2026-10-20, user decision: each item was its own prompt over the group's one line, so every item after the first was a repeat warning and never practised; 257 of 404 warnings on the real notes). Giving each item its own card was rejected because a card is its Canonical line (Identity below). The same day two rules were deleted rather than kept for the notes to follow: `Canonical answers:` is no longer a second spelling (3 uses against 1,636), and a path without items asks its heading instead of being a warning. `study/InterviewBank.kt` is its only owner and parses saved HTML with jsoup, added to the app in P3 at the backend's version (root `jsoupVersion`) because string matching cannot represent nested and loose lists. Amended 2026-10-21 (user decision): a question has one closed shape, written down for the notes in their repository's `core/reporead-contract.md`. Under its H3 come optional prompt material (paragraphs, lists, code blocks), then bold labels in this order: `Interviewer is testing:`, `A complete answer should:` followed by one flat bullet list, an optional `Worked answer:` with a web link, `Short answer:`, and the Canonical line last, linking at least one note. Anything else in an H3 is a warning naming the first rule it breaks. Before, every block besides the Canonical line was shown after the reveal as free text, so 13 questions' evidence appeared only with the answer (and their code not at all), and the checklist came in four spellings that no parser could split into points. A plain `Canonical answer:` without bold is now prose. When this was decided, none of the 1,740 real questions followed the shape; the notes were converted before it shipped (notes commit `72a3447`, [feature list](feature-list.md#closed-question-shape-2026-10-21)).
- **Identity** (amended 2026-10-19, audit PR4; decision D5). A question follows its bank document and Canonical line text, not its prompt, heading, block id or version. Matching uses the card's drawn text: a re-anchored Canonical-line edit can keep its card, while a larger edit can leave an orphan on the schedule beside a new question. Two prompts over one line in a bank keep the first in bank order and list the later prompt as an unrecognized warning; one prompt over two lines stays two. Review looks up the current question in the same up-to-date saved bank pages Practice reads; when no line matches, it shows the card's saved prompt with the bank to open instead of an answer (amended 2026-10-21; before, it showed the saved prompt with an answer from the saved page of the card's version). Uniqueness is local to this phone's cards; independently created cross-device duplicates may remain separate. No authored ids, fuzzy matching or question-editing feature is added.
- **Session.** The question alone, because attempting before seeing the answer helps even when the attempt fails (Kornell, Hays & Bjork 2009). Prompt material shows with the question. Then **Show answer**: the bank's Short answer (feedback is the real answer; Butler & Roediger 2008), what the interviewer is testing and the checklist (a standard to grade against; Rawson & Dunlosky 2007), and any worked solution. Each linked core section is a row that opens its note at that heading in the reader (amended 2026-10-21, user decision: once the Short answer carries the answer, the section is further reading, so the separately rendered section page was deleted rather than moved into a sheet). What each grade means is under **How to grade** in the session header rather than above the grades. Then Again, Hard, Good or Easy. The first grade saves the question as a card whose answer is its whole Canonical line, an authored mapping rather than an inferred one. Again brings it back in the session (ADR-13). Practice and Review sessions move through one pure `StudySession` (amended 2026-10-17): the items a session started with, the ones still to ask, and whether the answer is shown, kept whole across recreation. Whether an item's first grade is saved is read from what is stored (the cards made, the review log), never kept in the session, so recreation never saves a grade twice.
- **Answer preparation** (amended 2026-10-20, performance PR2; amended 2026-10-21). Practice and Review prepare the whole answer layout during the attempt, including its grades. `AnswerSlot` owns visibility, Compose opacity/semantics and the pointer shield; preparation never exposes the answer. Child controls, links and scrollers follow that visibility for keyboard-focus exclusion: a parent focus-properties rule stops at intervening scroller focus targets. A bank answer is Compose text from the parsed bank; its preparation is resolving the Canonical line's links among the repository's saved note list, two Room reads and zero HTTP calls. An early reveal waits rather than showing a partial answer. The native section page and its rules (alpha-0 VISIBLE WebView, separately blocked accessibility and focus) went with the section page on 2026-10-21. Review's answer is the same parsed bank question, so it parses nothing more before the reveal (amended 2026-10-21; before, it parsed the card's saved page again before each card). No cross-question pool, bank-parse cache, schema or dependency change.
- **Review** lives in the Practice tab (2026-10-14), with the same session flow: a first row saying how many cards are due, how many fall due next (tomorrow, or on the next day with cards) and how many in the 7 days after today (amended 2026-10-15), and a badge with the due count. Amended 2026-10-21 (user decision): it opens on what is due, then each topic with cards due and how many (`dueByTopic`, the same topics as Practice), so a session can cover one topic when there is no time for all; before, opening Review started a session of every due card at once. A session covers one topic's due cards or every topic's, up to the server's 40. A due card that cannot be graded is fixed in place (save the bank, or open it when it no longer asks the card's line); cards the server refused or whose note was removed start no session (Notebook lists them), and one refused or removed during a session says so and points to deleting it in its note (amended 2026-10-17).
- **What the card is** (amended 2026-10-19, audit PR4; amended 2026-10-21). The card is its Canonical line. Everything the answer shows (Short answer, checklist, worked solution, the rows' link texts) comes from the bank version the question is asked from: in Practice the saved version it was drawn from, in Review the current saved version that still asks the line (before 2026-10-21, the version the card was confirmed in). A linked note opens in the reader as a note in its own right, so the screen does not label a saved copy.
- **LeetCode study view** (P3) stays in `reader/ReaderStudyMode.kt`, separate from bank recognition in `study/InterviewBank.kt`: a fixed list of measured headings (`Approach`, `Brute Force Approach`, `Optimized Approach`, `Complexities`, `Mistakes`) collapses with CSS while `Problem` stays visible.
- Building a session makes 0 external calls and never downloads missing notes. No AI, multiple choice, or inferred answers.

**Consequences.** A topic without an interview folder has no questions. New banks, and new versions of banks, appear after a refresh and Save all: Practice asks only banks saved at their listed version, because a grade of a question from an older copy would be refused. Practice and Review load only notes in interview folders (`bankPages`) for question lookup: loading every saved page to find the 92 banks ran the app out of memory on 2026-10-14 (ADR-19). `InterviewBankCorpus` fails by name on a question without an answer line or a link to a missing note (1,740 questions at the last recorded run, 2026-10-21; [feature list](feature-list.md#closed-question-shape-2026-10-21)). Recorded intent: AI-drafted questions, later, as drafts the developer edits that never enter review automatically, once provider, privacy and cost are decided (LLM-written prompts were about a third unusable in a 2026 evaluation).

## ADR-21 — Metrics and logs are projections on a loopback port

**Decision** (Stage 6). Micrometer and Spring Boot Actuator serve only `health`, `metrics` and `info`, on management port `127.0.0.1:8082`, which neither `adb reverse` nor Caddy forwards. Meters are in memory and reset on restart; they are never application state. Logs name ids, SHAs, counts and outcomes, and metric tags never carry paths or content. Amended 2026-10-20: GitHub HTTP success/failure logs and oversized-response errors omit request paths, and repository-sync candidate/move events omit note paths, because they may name private notes; previously those logs exposed the path while metric tags excluded it. A failure says what failed (amended 2026-10-17): a refused request logs its code and message, which by contract hold no credentials or note content; a rejected sign-in, the OAuth error code of the step that failed, GitHub's own when GitHub refused (such as `bad_verification_code`, which Spring nests under its `invalid_token_response`); and every GitHub request that got no answer, its failure type (the endpoint is omitted under the 2026-10-20 privacy amendment). Before, the first two logged only the code and the exception class, and a GitHub timeout was counted but not logged. The deploy script prints only outcomes and the jar's SHA-256, because CI logs are public. Amended 2026-10-15: `info` names the Git commit the jar was built from, so which version is running can be checked on the host; before, only the jar's SHA-256 in the deploy log identified it. Amended 2026-10-21: each request has an id the server makes (`RequestLoggingFilter`, a UUID; the app never sends one). Every line logged while the request runs carries it, the response returns it in `X-Request-Id`, and one line records the method, raw request target, status and duration, so the app, which logs the id with every failed answer, can name the server's lines for a failure. The raw target includes query values, which can name a private note, except that the GitHub OAuth callback and app-code landing page log their whole query as `[REDACTED]` so one-time `code` and `state` values never enter the journal; keeping other query context is an accepted observability-over-log-privacy trade-off for this single-user system. Before, phone and server logs could be joined only by time. The VM's journal is set persistent and capped at 1 GB: the 2026-10-16 reboot erased the logs that explained it while it was volatile. `/var/log/journal` was created that day, so the default (`Storage=auto`) had kept logs since then without a cap. Amended 2026-10-21 (volume): in one day the journal took 49 MB, of which the backend's 827 lines were under 1 MB; the rest was Podman's health-check lines (13 MB, one per 10 s), conmon's "Broken pipe" warnings (6.5 MB, about 300 per dump, because `pg_restore --list` stops reading before the end of the dump it is fed), the Oracle Cloud Agent and its `sudo` sessions, and sshd probes. The Postgres health check runs every 30 s (a failing check is still filed), and `reporead-backup` reads the rest of the dump after the list, keeping `pg_restore`'s exit status. A log namespace for the backend (own retention cap) works on this VM's systemd but is not adopted: systemd's lines about the unit (exit status, restarts) and every other service stay in the default journal, `journalctl -u` without `--namespace` shows none of the backend's output, and Cockpit's Logs page passes no `--namespace` to `journalctl`. sshd's bot probes stay: a lower `LogLevel` would also drop successful logins. Amended 2026-10-21 (device logs): the device's own log lines reach the server's log, so the phone's are read without adb. `DeviceLog`, which replaces every `Log` call, writes each line to logcat and to a store on the phone capped at half the request body limit (read from `RequestBodyLimit` at build time), dropping the oldest lines first, so one `POST /api/app-logs` carries all of it. An upload is scheduled when the app starts, when it leaves the screen, and 2 s after each warning in any app process unless an upload already owns `sending.jsonl` (the delay puts the lines logged with a warning, such as a caller's own after `Api`'s, in its batch); it adds Android's record of why the app's processes ended (ANRs, native crashes, system kills) and deletes the lines only once the server has answered, so a lost answer can repeat them. A run sends at most two batches: the one a failed run left, then the lines stored since. A crash handler stores the crash first, then records its upload with WorkManager, waiting at most 2 s, before Android ends the process, so Android starts the app in the background to send it once there is a network. A failed upload is not retried on a backoff: its lines wait for the next request. Amended 2026-10-21 (sooner): before, a warning waited until the app left the screen and a crash until the app was opened again, too late to diagnose a crash by; a failed upload's exponential backoff (up to about 2 hours per wait) held every later request, since asking again while one waits changes nothing; and a run after a failure sent only the failed batch, so newer lines waited for another request. A crash cannot be sent from the dying process itself, and an ANR or native crash is known only from Android's record when any of the app's processes next starts. `RepoReadApplication` supplies the warning request when it starts `DeviceLog`, so warnings from background work are covered too. `DeviceLog` fires it only when `sending.jsonl` does not exist; warnings stored by an upload therefore cannot request another run, independently of WorkManager scheduling. The server writes each line under the `DeviceLogIngestController` logger with the phone's time and the version that logged it, and stores nothing. Device log lines are kept apart from the server's by logger name, not read as one timeline, because they arrive in batches, possibly hours late, and the phone's clock can differ; a failure is followed across both by its request id. A stored throwable keeps its classes, messages and frames, and the reader page's console errors and warnings become device log lines too: exception messages carry the explanation (a reader script failure carries the page's JS stack in one), and with one user the server's log holding that user's note text is accepted (user decision, 2026-10-21). Request targets and device log lines can therefore hold private content; callback codes and state, authorization headers and stored credentials are never logged. Were a second user allowed, their quotes would reach this log too. Rejected: Sentry or Crashlytics (crash data with a third party and a new dependency) and a separate journald stream (a native journald library or a rotated file, for a separation the logger name already gives). Logs are read in a browser through Cockpit, Oracle Linux's own web console, whose Logs page shows and searches the journal: one package, listening on loopback only and reached through an SSH tunnel, because the journal holds note text, with a login (`logview`) that can read the journal but not administer the VM. Rejected for now: Grafana with Loki and an agent, which would query app and server lines apart and keep a stack trace as one entry, for three more services to configure and update for one user; it is the step up if text search stops being enough. Each backend line starts with journald's priority prefix when stdout is the journal (`JournaldPriorityConverter`), because journald otherwise files every stdout line as info and the viewer's priority filter could not find a warning; device log lines go out at their own level, so they are filed the same way. An unhandled request failure is a server bug and is logged as ERROR, like the stack trace after it, so the error view shows exactly the bugs; refusals stay WARN. Lines frequent enough to crowd the phone's store out (one per scroll stop, copies, view toggles) go to logcat only (`DeviceLog.debug`).

**Consequences.** Metrics and logs are read on the host itself (SSH to the VM, or the Mac for debug builds). `GitHubHttpConfigurationTest` checks success, transport failure and oversize logging without request paths; `RepositorySnapshotRefreshTest` checks candidate-skip and move logs without note paths. `RequestLoggingFilterTest` checks one id across a request's lines and response, for refused, unauthenticated and unhandled requests, that ordinary query context remains visible, and that authentication-callback queries are redacted. The app's device test `ApiTest` checks a refused request carries the id (and logs it) and an unanswered one has none, and calls the upload route against the published API. The server's `DeviceLogIngestControllerTest` checks device lines are logged at their level with their version and phone time, cannot start a line that reads as the server's, and that a batch it cannot log is refused. On the device, `DeviceLogTest` checks that only a warning without a claimed batch requests an upload, a failed direct crash request does not request another, debug lines are not kept, one claimed batch is replayed after a lost acknowledgement, trimming stays within the cap, throwables keep their messages, and a torn last line is left out. `DeviceLogUploadTest` checks a pre-rename JSON line uploads with its original fields, lines are sent once and completed only after a 2xx, kept on failure without a retry, sent with the lines stored since in the next function call, completed on permanent refusal, held while signed out, and each process exit is logged once with Android's own description; `IsolatedPageTest` checks a page's console error becomes a device line. No automated test covers the crash handler's WorkManager handoff, the 2 s warning delay, or an actual worker's complete two-batch run. On 2026-10-22, `DeviceLogTest` and `DeviceLogUploadTest` passed together on a Pixel 8a (14 tests), including the `sending.jsonl` gate. A device E2E on that build verified the remaining crash behavior: `am crash` left no activity open, a background worker sent the stored crash and Android exit record successfully, an unavailable receiver produced exactly one failed POST and one failed worker result over 55 s while leaving the claimed batch replayable, and the next app start sent that batch and the two failure warnings in two POSTs. The warning's 2 s initial delay itself was not rechecked. `DeviceLog` owns logcat and the bounded line store; the worker in `sync/` owns sending, so the logger does not depend on the network layer that logs through it.

## ADR-22 — The phone's data stays on the phone

**Decision (amended 2026-10-19, audit PR2).** Ending a session never clears Room or image files. `Account` owns sign-in, sign-out and account deletion, one at a time in the application scope, with at most one backend call per operation and no retry. Sign-out attempts revocation, logs a typed failure and clears the session without a notice; the server session expires within 30 days. `Account` clears the session and reports `AccountDeleted` only on confirmation; a refused, unreachable or malformed answer, including a 401, reports `DeletionNotConfirmed`. A 401 can independently end the session at the HTTP boundary. Every outcome keeps saved pages, highlights, cards, grades, bookmarks and positions, including pending work. Saved notes remain readable signed out. Account notices persist until dismissed.

`SessionStore` owns only the encrypted session and pending PKCE verifier. A sign-in validates and consumes that verifier before its exchange; it records no data owner and sends no expected account id. `RepoReadApplication` owns one `PhoneSync` and its `NoteImages` per process; its first creation launches the ordinary image sweep even for a worker-only start. There is no pending removal, Retry, retirement or fresh-copy lifecycle, no account-operation gate in background work, and no account-driven back-stack reset or Save all cancellation/pruning. Local mutations and server answers still share PhoneSync's existing lock; accepted screen mutations remain cancellation-protected. Disconnect still removes the repository's local copy. Image reads and deletion still share their own lock and deletion generation; sweeps retain exactly Room's saved snapshots.

Backup/transfer exclusions and Keystore failure handling below are unchanged. Historical removal/ownership decisions below are no longer active.

**Consequences.** One phone holds one account's data at a time. Signing in as another GitHub account replaces acknowledged lists at the first sync (ADR-08); the existing sweep removes saved pages nothing lists and their images. Unsent work made before that switch can be sent under the new account: accepted for one user using one account, revisited before a second account is used. Server account deletion is not a phone wipe. An interrupted account operation leaves no cleanup to finish at startup; its remote outcome may be unknown. Files a normal image sweep cannot delete are logged for the next sweep.

**Current image-cleanup coverage (2026-10-20).** `NoteImagesTest` holds an HTTP image response, sweeps while it is in flight, then verifies the reader receives bytes without recreating the removed cache. A new fetch after the sweep can cache normally; generation remains in memory with no second deletion owner.

**Historical decisions through audit PR1 (superseded above where they differ).** `allowBackup=false` plus data-extraction rules excluding every domain, so neither cloud backup nor Android 12+ device-to-device transfer copies notes or the session (amended 2026-10-09). The session token is encrypted with an Android Keystore AES-GCM key. The stored session is deleted only when it can never be read (amended 2026-10-18; before, any Keystore failure deleted it, so a passing one meant signing in again, and stored text that did not parse crashed the app): text `save` could not have written (not two Base64 parts, an IV other than the 12 bytes Keystore's AES/GCM uses, a ciphertext shorter than the 16-byte tag), checked before the Keystore is called; `KeyPermanentlyInvalidatedException`; `UnrecoverableKeyException`, unless the Keystore error behind it is one Keystore marks transient or a system error rather than a fault of the key (`KeyStoreException.isTransientFailure`, `isSystemError`); or `AEADBadTagException` (a missing key is replaced by a new one before decrypting, so a lost key fails the tag check). Any other Keystore failure keeps the session and fails that request before it is sent (`SESSION_UNREADABLE`, status 0); background sync does not retry it, so the change waits for the next change or library open. The phone's data belongs to one account: a sign-in names it, and the server issues no session for any other account (`ACCOUNT_MISMATCH`), so a sign-in never removes that account's data. Amended 2026-10-18: data with no recorded owner (saved before owners were recorded, its session since ended) cannot be proven to be the signing-in account's, so that sign-in removes it first, as a sign-out would, and no session is issued over it; before, it was taken to be the new account's. Switching accounts takes **Sign out and remove from phone**, offered also after the session has ended (amended 2026-10-16: before, signing in as another account deleted the saved data, unsent changes included, without asking). Clearing runs under the same lock as every operation that writes the server's answers into Room, so an answer that arrives after the clear is never written back and handed to the next account (amended 2026-10-15: before, only sync runs took the lock, and a highlight the reader was still sending could reappear after sign-out). **Sign out and remove from phone** first says how many changes never reached the server, then deletes cached notes, images and those changes. Sign-out records a pending removal on disk before its one server call; account deletion records it only once the server confirms the deletion. Then the session is removed from disk, Save all is cancelled and its finished runs forgotten (ADR-19), Room and the files are cleared, and the pending removal and the data's owner are forgotten together, in one write, only once Room's rows and every file are gone (amended 2026-10-18). While the removal is pending the phone signs in as no account, and the first screen says where it stands: removing, files left, or the database could not be cleared, with **Retry**. The next start finishes it. A refused, unanswered or interrupted account deletion, or a 401, keeps everything on the phone: only the server's confirmation is evidence that the account is gone (amended 2026-10-18: before, the removal was recorded before the call, so an app that died before the answer deleted the phone's copy at its next start). Amended 2026-10-18: one owner, `Account` (constructed by `RepoReadApplication`), runs sign-in, sign-out and account deletion in the app's scope, one at a time, and publishes one state (idle with what the last operation reported, signing in, deleting the account, or removing with what stopped it); while one runs the root shows only the account screen, and a second tap starts nothing. Before, they ran in composable closures, so a rotation could cut off a sign-in or lose a deletion's message, and ordinary screens stayed open while sign-out waited for the server. The follow-up audit found that a listed-note predicate was not a lifetime boundary: the same account can list that id again, and a restarted worker bypassed activity startup. `Account` now retires the old `PhoneSync` (and its `NoteImages`) permanently when local removal is decided, and publishes a fresh instance only after successful cleanup. Local changes and server answers take the existing copy's lock; the clear waits for an admitted operation, while later calls on that instance cancel, even after re-sign-in. DAO note-existence predicates remain for disconnection within an active copy, not as removal authority. Both the activity and the workers (background sync, Save all) enter through Account's one startup job; a pending removal is finished before ordinary background work. No screen-job registry, epoch or second cleanup implementation exists. Account validates and consumes the pending PKCE verifier before legacy cleanup, so an unsolicited redirect cannot authorize deletion. Account notices render directly until explicitly dismissed; refresh and rotation do not own their lifetime. Before, the copy was deleted first, a file that would not delete stopped the app with the phone still signed in, and a missing session with a known owner, which an expired session also shows, stood for an unfinished removal. Amended 2026-10-18: saved pages record an immutable `snapshotCommitSha`, distinct from the Markdown blob and the repository's latest checkpoint. Images use one document/`commit-<sha>`/resolved-path cache layout and requests always carry that saved commit; embeds bind before the content boundary's single bounded serialization, never at image-fetch time. Room v14 keeps legacy text and pending changes with an unknown snapshot; old bare-blob cache folders are retired, and no current-image fallback is allowed. Cached reads and deletion share the file lock. Saved images are kept only for known snapshots Room holds a page of: one sweep derives them from Room after a page is saved, after the server's lists replace the saved ones, after a disconnect (answered, or already done on the server), at a clear and at each start, and an image fetch that began before a deletion does not write its image (an in-memory generation in `NoteImages`). Amended 2026-10-19 (audit PR1): the unused Notebook export and FileProvider are removed; no export writer or cleanup path remains.


## ADR-23 — How a change is verified

**Decision.**

- Backend tests run against real PostgreSQL 17.11 through Testcontainers, with explicit test-only GitHub mocks; no test depends on live GitHub.
- Layout belongs to formatters applied by Spotless: palantir-java-format for the backend's Java, ktfmt (Kotlin coding conventions) for the app's Kotlin, both at 120 columns. CI fails on unformatted code before running the tests (2026-10-15). `android/reader-web`'s JavaScript has no formatter.
- Real-corpus harnesses (`AnchorMeasurement`, `MoveMeasurement`, `BlobReadMeasurement`, `RenderedCorpus`, `InterviewBankCorpus`) are opt-in and point at a local clone outside the repository. Their outputs contain private note text and are never committed.
- Device tests run with `adb shell am instrument` on the phone used for reading, never `connectedDebugAndroidTest` (it uninstalls the app and its data). Success is the run's `OK (n tests)` line, not adb's exit code. CI only compiles them, and checks and bundles the reader without running it in a WebView (amended 2026-10-18). Screens under test run in one debug-only, non-exported `TestHostActivity`, absent from release, and are asserted through Compose semantics with `ui-test-junit4` from the app's Compose BOM (amended 2026-10-19).
- Records distinguish automated checks, device checks and observations made by hand; a gate never passes on mocks or a build alone. Real data is backed up before a migration runs on it. Test edits to the notes repository go only under `scratch/`.

**Consequences.** Live GitHub behaviour (history rewrites, missing blobs) is mostly proven by tests, not on the real system; [the feature list](feature-list.md#not-yet-verified-on-the-real-system) says which.

## ADR-24 — Migrations keep the previous release working; a failed deploy is undone by hand

**Decision** (2026-10-17). From V15, a migration leaves a schema the previous release still runs on. It adds: tables, nullable columns, columns with a default, indexes. A step that removes or requires something (dropping or renaming a table or column, changing a column's type, making a column required, adding a required column without a default) goes in a later release, once no deployed release uses what it removes, and its migration carries a `-- Contract:` line saying which release stopped using it. `ExpandOnlyMigrationsTest` fails the build on such a step without that line. The API already changes this way: a field the app reads is removed only after the release that stops reading it is installed, as the four-step H5 rollout did. Amended 2026-10-18: two replacements did not wait, by the user's decision: the snapshot-pinned image contract and deleting the five per-list routes (ADR-08). A release older than them is unsupported once that backend deploys; the phone installs the matching release from GitHub Releases (ADR-15). A deploy writes a database dump just before the restart and, if the new jar is not healthy, fails the run and leaves the new jar in place (`backend/deploy/reporead-deploy`). Going back is a person's call: put the previous jar back, which this rule makes safe, or, when the data itself must go back, restore the deploy dump into an empty database first.

**Why.** Putting the previous jar back is safe only when it runs on the schema the new one left. V13 and V14 dropped columns in the same release that stopped reading them, so the release before each could not run after it, and the deploy script restored the previous jar automatically onto exactly such a schema. Considered and rejected: restoring the database automatically with the jar (a destructive step run unattended, which loses any write made after the dump), and down-migrations (Flyway's undo needs a paid edition, and a dropped column's data cannot come back). Rolling forward with a fix is the default; the dump is for a damaged database.

**Consequences.** Removing a column takes two releases: one that stops using it, then one that drops it. The `-- Contract:` line is a claim the test cannot check; review does. The deploy script does not put the previous jar back even when this rule makes it safe, so a failed deploy waits for a person.

## ADR-25 — What a screen draws over its content is one value with one owner, kept across recreation

**Context.** The reader held what was drawn over the note in separate Compose states, only some saved across recreation: rotating while writing a note lost the text and the dialog, and the highlight being reattached lost its mode. Whether the page had finished rendering was private to `ReaderSession`, so controls that use the page were offered before it could answer them, and did nothing or said the passage was missing.

**Decision** (2026-10-17). What can be over the note is one sealed `ReaderOverlay` owned by `ReaderScreen`: a question or note being written, a highlight's edit, deletion or conflicting edit, a link's preview or choices, and the outline. It is kept with `rememberSaveable`, so at most one is open and it comes back after recreation with what was typed; the rows it holds are `Serializable` (no Parcelize plugin). The notes panel reports which row the user picked; the reader runs the action, so one exhaustive `when` draws every overlay. A mode that must stay usable beside an overlay, such as reattaching (the outline helps find the passage), is its own saved state. State a screen needs from another owner is read as that owner's observable state, never inferred: `ReaderSession.outline` exists only while the page is open, and `opened` is derived from it; together they decide when Outline, Study, Show and a changed section's link are offered, so a page that did not render, or whose renderer is gone, offers none of them.

**Consequences.** Two overlays cannot be open at once by construction. A row kept in saved state is a snapshot: an edit made from it after a sync changed it is refused as a conflict (409), which the conflict overlay handles. No ViewModel: navigation stays the app's own back stack (§4 of the architecture), and saved state covers recreation and process death. Amended 2026-10-19: the back stack is now Navigation 3's ([ADR-27](#adr-27--navigation-3-owns-the-back-stack-saved-screen-state-belongs-to-its-entry-and-its-format)); each entry keeps saved state and a ViewModel store while it is in the stack. Amended again 2026-10-19: "No ViewModel" is superseded by [ADR-28](#adr-28--a-screens-work-belongs-to-its-entrys-viewmodel-a-confirmed-change-belongs-to-phonesync): the reader's work and the highlight being reattached belong to its entry's ViewModel. Unsubmitted overlays remain the one saveable UI value. Submitted edits and conflicts stay ViewModel-owned; only the submitted id/text is restored, and a conflict is drawn only when no UI overlay is open.

**Evidence.** `ReaderLifecycleTest`: a note being edited and a highlight being reattached survive recreation, a page that never becomes ready offers no Show, and a page whose renderer stops no longer offers Outline; each fails on the code before. 

## ADR-26 — One owner for the app's side of the HTTP contract

**Context.** Routes, coercive JSON getters and nullable status handling were spread across consumers. A malformed library could become local state, an out-of-range instant could crash after a successful save, and an unknown/malformed 409 could authorize dropping pending work. Moving getters into DTOs alone would leave producer drift and refusal authority unresolved.

**Decision** (2026-10-18). `Api` owns one named function per app-used route, exact success statuses, existing caps and echoed request correspondence; generic execution is private and each route makes at most one HTTP request, without retries, redirects or alternate strategies. The wire models are generated from the backend's published API (amended below); `WireRules.kt` owns decoded-answer value rules a generated shape cannot state. `WireJson.kt` owns one JSON policy: additive fields allowed, required-nullable keys present, no scalar coercion, and instants must fit epoch milliseconds. Small scalar serializers close kotlinx.serialization's quoted-number/boolean coercions; generated serializers own structure. The serialization plugin is 2.2.10 and JSON runtime 1.9.0, verified with the existing toolchain, not a toolchain upgrade.

`WireMappings.kt` maps decoded records to database entities before acknowledgement or Room replacement. `PhoneSync` alone owns positive item-refusal status/code pairs; unknown, malformed, oversized or wrong-status answers are not authority to discard work. Account identity stays with SignIn and review-to-local-card identity with PhoneSync. The library's existing transaction and all other storage/lifetime owners remain unchanged. Transport and decoder causes are retained without logging bodies or credentials.

The backend remains the owner of published meanings. Amended 2026-10-18 (generated wire models): the backend publishes them as `backend/openapi.json`, and the app no longer declares any shape by hand.

- **Derivation.** `OpenApiSpecTest` runs springdoc 3.1.1 (built on Spring Boot 4.1.0; a test dependency only, so production serves no spec) over the `/api/**` controllers and records and fails when the committed file differs, rewriting it to the derived spec. A backend change therefore reaches the app only through the rewritten, committed file. Committed rather than derived during the app build, because deriving needs the whole Spring context and PostgreSQL, which Android builds and the release job do not have. OpenAPI 3.0, no servers (debug and hosted builds reach different hosts), keys sorted.
- **Rules beyond springdoc's own.** A nested type is named with its enclosing types (`DocumentController.Content` is `DocumentControllerContent`), and a second type under a used name fails derivation; bare names would have produced `Result`, `State` and `Content`, and collisions would merge silently. Response properties are required because the application mapper writes every record component, nulls included. Optional input fields explicitly declare omission with standard `@Schema` metadata on their declaring accessor; JSpecify `@Nullable` separately declares nullability. Reading anchors use distinct request/response records because input may omit the prefix but output must include its nullable key. Both client models are generated; no handwritten client shape or compatibility alias is introduced. Boxed required request numbers remain non-null. `LibraryController` names the top-level `LibrarySnapshot` for its measured bytes with a compile-only swagger annotation.
- **Actual serialization.** springdoc reads records through swagger-core's Jackson 2; clients get the application's Jackson 3 mapper. The same test serializes a test-only sample of every published record, once with each `@Nullable` component null and once with values, and requires it to match its schema: the same keys, all present, the published types and enum values, and null exactly where nullable. This is where `@JsonUnwrapped` (`LibraryRepository`) and `@JsonValue` (`Annotations.Location` as a passage) must agree.
- **App generation.** The `wireModels` task (OpenAPI Generator 7.25.0, kotlin, kotlinx.serialization, models only) generates `network/wire/` into the build directory at build time; nothing generated is committed or edited. Integers, longs and booleans map to `WireInt`/`WireLong`/`WireBoolean`, aliases whose only purpose is that the generator marks them `@Contextual`, so `wireJson`'s module decodes them with the strict serializers; times are `@Contextual` `Instant`s the same way. Generated constructors list properties alphabetically, so every app construction names its arguments.
- **Not generated.** The error envelope (`ApiErrors.Body`) stays a private type in `Api`: the spec publishes route answers, not the advice around every failure, and the app reads `code` as text because a newer server may send codes it does not know; only known pairs authorize anything. Generation also does not establish that an answer belongs to its request (Api routes), prevent truncated delivery (HttpURLConnection framing, `ApiTest`), or make a change compatible with an app already installed.
- **Routes checked against the spec** (amended 2026-10-21). Only the models are generated; `Api`'s method, path, query, success statuses and answer type per route stay typed by hand, so a route renamed on the backend compiled and failed only on a phone (safely: an unknown route's 404 is not RepoRead's `NOT_FOUND`, so work stays pending). A generated client would bring its own HTTP stack and still need `Api`'s caps, correspondence and error rules on top. Instead the build puts `backend/openapi.json` into the device tests' assets (`publishedApiAsset`), and `ApiTest`'s every-route test checks each request it records: it reaches exactly one published operation, sends the published query parameters, is answered with exactly the published statuses, and decodes into the published schema. It runs with the device suite, not in CI: the JVM's `HttpURLConnection` refuses `PATCH`, so a JVM test could not send `editAnnotation` without a fake transport, and the device suite already runs after every backend change.

**Consequences.** The old public raw verbs, HTTP JSON builders, `ServerJson.kt` and its superseded tests are removed with every caller migrated. The generated models replaced `Contract.kt`, the nine `*WireContractTest` producer tests, `ContractFixtures` and 27 shape-only JSON examples; `item-refusals.json` remains, checked by `ItemRefusalsTest` and read by the app's `RefusalTest`. Test answers are built with the generated constructors (`WireSamples.kt`, shared by the JVM and device tests), so a backend shape change fails test compilation, which CI runs for the device tests too. The app now requires every published field, not only the ones it reads; removing a published field was already incompatible. Room and the reader bridge are unchanged. Optional request defaults may be omitted; actual HTTP tests verify missing and explicit-null owner/prefix inputs while response decoding stays strict. Strict decoding can expose previously hidden server/client drift; it leaves saved data and uncertain pending work untouched rather than inventing defaults. Step 9 also replaces transient PhoneSync refusal sentences with structured operation results rendered by the consuming UI. Existing durable annotation/review rejection text and Room schemas are unchanged; their redesign is not part of this wire-boundary replacement. Credential lifecycle ordering is owned by GitHubTokenLifecycle (ADR-03), and fixed runtime SQL/socket deadlines by the backend application configuration. [API contract PR #70](https://github.com/jaxwong/reporead/pull/70) records commands, results, size justification and live exclusions.

## ADR-27 — Navigation 3 owns the back stack; saved screen state belongs to its entry and its format

**Context.** The app kept its own back stack: a list of `Screen` values encoded as strings (`encode`, `decode`, `StackSaver`), each entry's saved state keyed by its stack index and encoded screen (`entryKey`, `screenStates`, `keptStates`, `key(...)`) and its own `BackHandler`, about 100 lines. An entry had no lifetime of its own, so nothing could be owned by one, which is what the Android foundations plan needs next: a screen's work outliving rotation and being covered.

**Decision** (2026-10-19).

- **The stack.** Navigation 3 (`navigation3-runtime`, `navigation3-ui` 1.2.0) owns it. Destinations are `@Serializable` `Screen` and `OpenAt` values; the key is `Entry(id, screen)`, with a new random id at each push. The stack is saved with `NavBackStackSerializer(Entry.serializer())`: typed, so no reflection and no casts. The id, never the screen or its position, identifies an entry, so a note opened from a note that links back keeps two separate states.
- **The account screen.** `rememberDecoratedNavEntries`, with the saved-state and ViewModel-store decorators, runs above the account screen, and `NavDisplay` below it. Account operations hide the stack without popping it; sign-out and account deletion keep the entries and their saved state (audit PR2, 2026-10-19). The former removal/fresh-copy resets, including ownerless-sign-in cleanup, are retired (ADR-22). Entries are rebuilt when the stack changes; their content reads current account and sign-in state when it draws.
- **Back.** `NavDisplay` draws only the top entry, with no transition, as before. System Back pops the top entry and is off at the root, so the activity handles it there. A screen's own Back removes its own entry, so a repeated tap on a screen already left does nothing; before, it popped the screen below.
- **Restoring saved state.** `MainActivity` records saved UI format **5** (initially 1; foundations PR4 advanced it to 2, audit PR1 to 3, the study-package moves to 4, and the database entity/package move to 5) and calls `compatibleSavedState` before `super.onCreate`. Unmarked or incompatible formats reset navigation/UI state; compatible later builds retain it. The marker changes only for an incompatible saved-state format, never for an ordinary release. Format 3 may serialize `library.StudySession`; format 4 may serialize the former database entity class names held by reader overlays. Navigation, drafts and in-progress sessions reset; Room, files and pending changes are untouched. Compose keys saved UI state by position: the old string-list stack cannot be read as the new serialized stack. The debug test host applies the same policy at its actual Activity boundary; it never opens the app's real store. `MainActivity` wiring itself remains checked by review, not by launching the live app in tests.
- **Dependencies.** navigation3 1.2.0 requires AGP 9.1.0 and compileSdk 37 (its AAR metadata); the repository has AGP 9.1.1 and compileSdk 37, so nothing in the toolchain changed. Navigation 3 selected Lifecycle 2.10.0, SavedState 1.4.0 and NavigationEvent 1.1.1; Compose UI/runtime/animation/foundation remain 1.12.0, Material3 1.4.0, Kotlin stdlib 2.2.10 and serialization 1.9.0. On 2026-10-19 the user approved adding `lifecycle-viewmodel-navigation3:2.10.0` now, plus a direct androidTest declaration of `lifecycle-viewmodel-compose:2.10.0` for the labelled owner probe. This avoids the proposed Lifecycle 2.11.0/toolchain upgrade. The decorators follow [Android's state guidance](https://developer.android.com/guide/navigation/navigation-3/save-state).

**Consequences.** `encode`, `decode`, `StackSaver`, `entryKey`, `ROOT_STATE`, `screenStates`, `keptStates`, `key(...)`, `BackHandler` and the JVM `NavigationTest` of the encoder are deleted. Its assertion that pre-upgrade stacks restore is replaced by the reset above. Screens still own their work through composition, so a rotation still cancels it (ADR-25; the plan's PR 4). Amended 2026-10-19: superseded by [ADR-28](#adr-28--a-screens-work-belongs-to-its-entrys-viewmodel-a-confirmed-change-belongs-to-phonesync); `lifecycle-viewmodel-compose` is now a production dependency.

**Historical evidence before the audit follow-up.** The earlier Pixel 8a run drove `RepoReadApp` over isolated data: A → B → A panels, recreation, synthetic-registry restoration through a Parcel, account gates, fresh-root sign-out, loss confirmations/Cancel, confirmed disconnect, and repeated Back. The real Dev app's update returned to a fresh Library with saved data intact; `am kill`/Recents restored its note and panel. That update discarded saved state before the app saw it, so it was not proof of the migration filter. The old helper-only build-filter tests and synthetic registry host are now replaced, not retained in parallel.

**Audit follow-up tests** (historical; audit PR2 retires ownerless-sign-in cleanup and tests session changes preserving data instead). `AppNavigationTest` added ownerless sign-in cleanup, refusal then an explicit second attempt, and a legacy-format Activity restore that preserves Room, a pending annotation and a test-only file. Its compatible restore now uses the real Activity saved-instance-state Bundle through a Parcel into a fresh Activity. `NavigationTest` retains every destination/entry-id round-trip and tests format acceptance independently of build number. The legacy fixture is the literal c3a55f9 `StackSaver` string-list format inside Android-generated Activity state, not an APK-captured Bundle or a retained legacy encoder. `EntryLifetimeTest` puts labelled test-only ViewModels in a real `NavDisplay` with the same hoisted public decorators: equal destinations have separate owners/drafts, cover/recreation keeps them, pop/removal clears them, and fresh-Activity restoration recreates owners while preserving ids/drafts. It has no production hook; actual screen ViewModels and their work remain PR 4, which must rerun these assertions with those owners.

## ADR-28 — A screen's work belongs to its entry's ViewModel; a confirmed change belongs to PhoneSync

**Context.** ADR-27 gave each back-stack entry a lifetime, but screens still ran their work in composition: `rememberCoroutineScope`, `RefreshOnEntry` and `rememberLoad`, and the reader launched highlight changes in the app's scope that wrote into composition state. A rotation or a covering screen cancelled or repeated a refresh, a disconnect preview, a connect, an export or a card confirmation and lost what it reported. `PhoneSync`'s lock orders local writes and server answers, but does not stop a caller's cancellation from discarding the local commit of a change the server had confirmed.

**Decision** (2026-10-19, Android foundations PR 4).

- **Owners.** Library, Folder, Available, Practice, Review and Reader each have one plain `ViewModel` in the screen's file, created with `viewModel { }` inside its decorated entry and given only what it uses (`PhoneSync`, `RepoReadDao`, `Api`, the `Application` for Save all). No factory class, DI, base class, repository or use case. Search and Notebook only read Room and have none. Each ViewModel exposes one immutable `StateFlow` and one function per user action; screens collect it, and Room's flows, with `collectAsStateWithLifecycle`. No ViewModel holds an Activity, a WebView or a composition callback.
- **Admission.** Folder has one operation value; Library one sync, Available one connect, Practice/Review one grade and Reader one server change (Review's card confirmation was deleted on 2026-10-21, ADR-13). Admission is synchronous: a duplicate or busy request queues nothing and logs the entry and operation. Reader edit/delete dialogs close only after admission; a rejected edit keeps its text. The displayed page is fixed per reader entry.
- **When loads run.** On entry creation, after a sign-in, and when asked (pull, Send changes, Try again). Collection restarting starts nothing. Library and the folder root also load when returned to, as before: B1, which would stop that, is not approved. A return is told from a rotation by `isChangingConfigurations` when the screen leaves composition. The reader's page and highlights no longer reload on a rotation or a return.
- **Results the screen acts on.** Disconnect, connect and followed-link/recovered-editor results are claimed once by the current UI. A pending overlay never overwrites another editor. Conflicts remain ViewModel-owned until resolved, drawn only when no UI overlay is open. Navigation runs in `LifecycleResumeEffect`: rotation cannot repeat it, a covered entry waits and a popped entry never acts. No Channel, SharedFlow or queue; no mutation or platform effect is replayed after process death.
- **What stays UI state.** Tabs, filters, panels, unsubmitted editor text, study mode and the reader's one UI overlay (ADR-25) stay `rememberSaveable`. `SavedStateHandle` restores Practice/Review session progress/start, the reader's reattachment, and a submitted edit's mutation id/text. Restoring an edit reloads its annotation from Room into a non-running conflict, or recognises an already-saved/deleted edit; it never resends it. A failed edit returns its draft to a UI editor, removing the operation's saved input when claimed. Current saved-state format **5** rejects format 4's former database entity class names; format 4 rejected format 3's former `library.StudySession` class, format 3 rejected the retired figure destination, and format 2 rejected pre-foundations-PR4 format 1's incompatible Compose-owned sessions (ADR-27). This uses the existing incompatible-format policy, not a per-build reset; Room, files and pending changes are preserved.
- **Committed mutations.** `PhoneSync.committed` protects local writes and finite online mutations through their local commits. Audit PR2 removes retirement and cleanup; one PhoneSync serves the process, and account operations never refuse local writes. Read-only loads, disconnect preview, pending-change passes and dismissing refused grades stay cancellable. `PhoneSync.connect` saves the library before reporting success. Amended by audit PR4: Practice and Review admission run inside their DAO write transactions under `PhoneSync.committed` (ADR-13). This replaces the temporary caller-side cancellation protection and the two separate writes; cancellation protection alone never made them atomic.
- **Calls.** The backend README owns GitHub ceilings. `PhoneSync.connect` makes 2 backend requests (connect and library), with at most 1 GitHub call in total; `gradeNewCard` makes 0 external calls. Nothing retries. Api's timeouts remain 15 s connect and 45 s read per call; audit PR2 removes the account-removal wait.

Amended 2026-10-19: section summaries and their baseline/acknowledgement state, the unused full-screen figure, and Notebook export are retired. Notebook now only reads Room and needs no ViewModel; saved UI format 3 rejects back stacks containing the removed figure destination. Reattachment and submitted-edit restoration remain unchanged.

**Why.** Standard entry ViewModels replace composition-owned work; claimed state keeps navigation/platform effects in the current UI ([Android UI-event guidance](https://developer.android.com/topic/architecture/ui-layer/events)). Minimal submitted input restores a conflict without saving stale server metadata or replaying a command. The audit follow-up adds production lines for this restoration contract and visible rejection/draft recovery; it removes the old saveable conflict and general version-pair comparison machinery rather than keeping parallel paths.

**Consequences.** `RefreshOnEntry`, `rememberLoad`, Available's connect helper and the reader's app-scope writes are deleted. `appScope` reaches only `ReaderSession`, whose page work and position saves are unchanged; `rememberCoroutineScope` only scrolls the reader's WebView. Leaving a reader while a new highlight is sent cancels the foreground send; it is saved, and the background sync sends it (ADR-08). A folder preview or refresh now disables the folder's other actions. Device tests host screens in the production `rememberEntries`/`ShownEntry` (`TestEntries`); `lifecycle-viewmodel-compose`, `lifecycle-runtime-compose` and `lifecycle-viewmodel-savedstate` are declared at the Lifecycle 2.10.0 already resolved.

**Historical evidence before audit PR1** (2026-10-19; the summary/export-only cases below were retired with their features). Reproduced before the fix: the new `AppNavigationTest` cases, built against `main` (c1f4a90) with only the test files changed, failed 12 of 14: T1 (preview through recreation), T2 (connect through recreation), T3 (no sync on recreation), T4 (refresh while covered), rotation during a refresh, T5 (edit outcome after recreation), T9 for disconnect and connect, T10 (real 45 s timeout, then a retry), T11 (export), T14 (double-tapped refresh) and T16 (summary fetched while covered). A restored folder replaying nothing (T15) and a double-tapped Sync now pass on `main` too and stay as regression guards. On this change, the Pixel 8a device suite passed, `OK (173 tests)` (APK b32c8a2c27ea4721), with the README checks (`spotlessCheck`, `lintDebug`, `testDebugUnitTest`, both assemblies) exiting 0. Beyond those: `CommittedMutationTest` (each mutation committed once after its caller is cancelled, within its call count; queued local writes; retirement refusing a queued write; card and first grade together), `NotebookExportTest` (T11), T15 restoration of a practice session and of a folder, T17 (a failed load keeps saved notes; an empty repository says so) and `ReaderViewModelTest` (T14 at the action boundary). Not verified: the phone end-to-end table (rotation settings, `am kill`, `install -r`; each needs approval), live GitHub connect, refresh and disconnect, a missing share target, and process death during a committed mutation, whose outcome is the existing pending/unknown handling; exactly-once effects across process death are not promised.
